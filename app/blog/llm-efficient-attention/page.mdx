# 高效注意力：KV Cache · GQA · Flash Attention

<SeriesNav series="llm" />

标准 Self-Attention 在序列长度上是平方级的：长度翻倍，矩阵翻 4 倍。训练 1024 token 还能忍，推理时一边自回归生成 4096 token，一边把过去所有 token 的 K、V 重算一遍——又慢、又费显存，长一点就直接顶满 GPU。

把这件事拆开看，问题分布在三个地方。一是推理时大量重复计算，本来不必算的过去 token 又被算了一遍，KV Cache 解决它；二是即使缓存了 KV，序列变长后显存还是吃不消，GQA 在结构上动刀子；三是计算本身的瓶颈不是浮点而是 HBM 来回搬数据，Flash Attention 改写算法让数据待在片上 SRAM。

三个方法叠在一起，是当前所有线上推理框架的默认配方。

## 推理时的重复计算

自回归解码每一步都把当前为止的全部 token 喂给模型：

```text
step 1: 输入 "The"          → 算 K1,V1   → 预测 "cat"
step 2: 输入 "The cat"      → 算 K1,V1,K2,V2 → 预测 "sat"
step 3: 输入 "The cat sat"  → 算 K1,V1,K2,V2,K3,V3 → 预测 "on"
```

第 1000 步要重新算 999 个历史 token 的 K、V。总计算量是 <Math>{`O(N^2)`}</Math>，其中 99% 是重复劳动。

## KV Cache：只算新 token

观察一下因果注意力的结构：每个位置的 K、V 只取决于它自己之前的输入，不会被后来的 token 改变。那就把它们存起来，每步只算一个新 token 的 Q、K、V，再让 Q 和缓存好的 K 做 attention。

<Math block>{`\\text{cost without cache} = O(N^2), \\quad \\text{cost with cache} = O(N)`}</Math>

实测一下，在一个 256 维 8 头的小模型上生成 128 个 token：

| 设置 | 用时 | 加速比 |
|---|---:|---:|
| 无 KV Cache | 0.250 s | 1× |
| 有 KV Cache | 0.031 s | 8.1× |

理论上的加速比是序列长度量级的，实测差距小一些是因为还有别的常数项开销（layer norm、位置编码、采样等）。

## GQA：让多个 Q 共享 KV

KV Cache 解决了重复算的问题，代价是要把所有历史 K、V 都摆在显存里。LLaMA-2 70B 这种规模的模型，单条序列就能吃掉惊人的一块。

KV Cache 的显存占用可以直接写出来：

<Math block>{`\\text{KV bytes} = 2 \\cdot L \\cdot N \\cdot h_{kv} \\cdot d_{head} \\cdot s`}</Math>

L 是层数，N 是序列长度，<Math>{`h_{kv}`}</Math> 是 KV head 数，<Math>{`d_{head}`}</Math> 是每个 head 的维度，s 是数据精度的字节数。所有项里只有 <Math>{`h_{kv}`}</Math> 是结构上能调的——那就把它从 Q head 数解耦出来。

<KvCacheGrowth />

GQA 的做法：让多个 Q head 共用一组 K/V。极端情况下所有 Q 共享一组 KV（MQA），中间档是分成若干组（GQA-N）。

<GqaHeadGrouping />

参数和效果在小模型上对比一下（1 层 8 Q-head）：

| 配置 | KV 参数 | val loss | 与 MHA 差 |
|---|---:|---:|---:|
| MHA (8Q / 8KV) | 32,768 | 2.317 | baseline |
| GQA (8Q / 4KV) | 16,384 | 2.305 | -0.011 |
| GQA (8Q / 2KV) | 8,192 | 2.349 | +0.032 |
| MQA (8Q / 1KV) | 4,096 | 2.465 | +0.149 |

GQA-4 显存减半，loss 反而略好一点（可以看作一种正则化）。MQA 把显存压到 1/8，但效果掉得明显。LLaMA-2 70B 选了 GQA-8（64 Q / 8 KV），是当下大多数大模型的折中点。

## Flash Attention：把瓶颈移出 HBM

到这里显存已经省了不少，但 attention 的计算速度还有问题——不是因为 GPU 算不过来，而是数据搬运不够快。

H100 的 FP16 算力是 989 TFLOPS，HBM 带宽是 3 TB/s。算一个 attention 矩阵 N=4K，要在 HBM 里来回写一张 64MB 的中间结果，瓶颈就卡在带宽上，算力被白白浪费。

朴素实现是这样三步：

```text
1. Q × K^T → 整张 N×N 矩阵写入 HBM
2. 从 HBM 读 → softmax → 写回 HBM
3. 从 HBM 读 → × V → 写回输出
```

Flash Attention 的核心想法是把这三步在一个 kernel 里完成，永远不把整张 N×N 矩阵物化到 HBM。它把 Q、K、V 切成小块（tile），每对 tile 在片上 SRAM 完成 score、softmax、乘 V 三件事，再合并。

<FlashAttentionTiling />

合并的关键是 online softmax。普通 softmax 需要看到全行才能算分母（要先求 max 再求 exp 和），分块时根本看不到。Flash 的做法是边算边维护一个滚动的 max 和归一化项：

<Math block>{`m^{(j)} = \\max(m^{(j-1)},\\, m_j),\\quad \\ell^{(j)} = e^{m^{(j-1)} - m^{(j)}}\\, \\ell^{(j-1)} + e^{m_j - m^{(j)}}\\, \\ell_j`}</Math>

每加进来一个新 tile，就用新的 max 修正旧的累计，结果在数学上和一次性算整行的 softmax 完全等价。换来的是显存从 <Math>{`O(N^2)`}</Math> 降到 <Math>{`O(N)`}</Math>，速度也快 2–4×。PyTorch 2.0 之后内置了一行调用：

```python
y = F.scaled_dot_product_attention(q, k, v, is_causal=True)
```

CUDA 可用时会自动走 Flash 路径。

## 三件事叠起来

把上面三个优化按顺序叠加，看不同序列长度下的总显存：

<AttentionMemoryRoofline />

朴素方案在 8K 就开始爆，加 KV Cache 能撑到 32K，再上 GQA 能撑到 128K 附近，最后 Flash Attention 把激活那一份也吃掉。线上推理框架（vLLM、TensorRT-LLM、TGI）默认都把这三件事打包起来。

| 优化 | 解决什么 | 量级 |
|---|---|---|
| KV Cache | 推理重复计算 | ~10× 加速 |
| GQA | KV Cache 显存 | 2–8× 显存减少 |
| Flash Attention | HBM 瓶颈 | 2–4× 加速 + 激活内存 O(N²)→O(N) |

## 工业界还在改什么

KV Cache 在多请求场景下的内存碎片是个老问题——每个请求长度不一，预分配会浪费，不预分配又会碎掉。vLLM 的 PagedAttention 借鉴操作系统页表的思路，把 KV Cache 切成固定大小的物理块，用一张索引表把同一请求的逻辑序列拼起来。这一层让多请求共享显存，能把 GPU 利用率从 30% 提到 80% 以上。

Flash Attention 也在快速演进。FA-2 重写了反向传播减少非矩阵 GEMM，FA-3 在 Hopper 架构上利用 TMA（Tensor Memory Accelerator）和 FP8 Tensor Core 把吞吐又拉高一截。这些都是工程层面的改进，数学骨架没动。

| 环节 | 这个项目 | vLLM / TGI 级别 |
|---|---|---|
| KV Cache | Python list 逐步追加 | PagedAttention，固定 block 共享 |
| GQA | `repeat_interleave` | 融合 CUDA kernel |
| Flash Attention | PyTorch SDPA | FlashAttention-3 + FP8 |
| 序列长度 | 64–256 | 128K+ |
| 并发 | 单请求 | Continuous Batching |
