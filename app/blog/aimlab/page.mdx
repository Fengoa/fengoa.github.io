# 用 React Three Fiber 实现一个 3D 瞄准训练器

点下「开始」，鼠标被锁进画面，手腕转动带动视野旋转，屏幕正中的准星扫过一片蓝色小球，左键扣下，最近的那颗亮起分数后换到别处。整段体验不依赖任何原生客户端，完全运行在浏览器中。

瞄准训练器（Aim Lab、Kovaak's 等）用来练习射击精度。要把它放进浏览器，需要组合几类 3D 应用的基础构件：每帧刷新的场景、画面与界面共享读写的状态、第一人称视角控制、把靶子摆到合理位置的空间几何、从准星射出并判断命中的射线。下文按从按下开始到扣下扳机的顺序讲解这些构件，并在每处说明当时的选择依据。

---

## 1. 技术基础

页面基于 Next.js（App Router）与 React 19。3D 部分由 React Three Fiber 承担，它以 React 组件描述 three.js 场景，drei 补充环境贴图、`Html`、`useGLTF` 等常用组件。three.js 负责绘制，zustand 作为 3D 世界与上层界面之间共享的状态容器，Tailwind CSS v4 处理样式。

一个常见误区是认为 3D 游戏和 React 应用互不相关。在 React Three Fiber 中两者属于同一棵组件树：`<mesh>`、`<sphereGeometry>` 这类标签会被映射为 three 的对象，每帧通过 `useFrame` 修改其属性，状态由 zustand 统一管理。后续内容都建立在这个模型上。

---

## 2. 架构：双层渲染与 SSR 隔离

画面由 3D 层与 2D 层叠加构成。3D 层是 React Three Fiber 的 `<Canvas>`，渲染 three.js 世界；2D 层是叠加在 Canvas 之上的 DOM，承载分数与调参面板，通过 `fixed`/`absolute` 与 `z-index` 定位。

两层共用一个 zustand store（`useGame`）。3D 侧在 `useFrame` 中写入相机朝向、位置、按键状态；2D 侧用选择器订阅 `score`、`hits`、`shots` 等切片。命中与计分逻辑集中在 store 处理。

重型 3D 子树经 `next/dynamic` 以 `ssr:false` 导入（`app/components/Game.tsx:10`）。WebGL 依赖浏览器环境，服务端缺少 `window`，直接渲染会抛异常。隔离为 `ssr:false` 后，首屏 HTML 可立即返回，Canvas 随后在客户端挂载。

```tsx
// app/components/Game.tsx
const Experience = dynamic(() => import("./Experience"), { ssr: false });

export default function Game() {
  return (
    <div className="relative h-screen w-screen overflow-hidden bg-black">
      <Canvas flat shadows="percentage" camera={{ fov: 75, near: 0.1, far: 200 }}>
        <Experience />
      </Canvas>
    </div>
  );
}
```

### 2.1 选择依据：首屏是否直接挂载 Canvas

首屏直接挂载 Canvas、不区分服务端渲染会触发 WebGL 在 `window` 缺失时抛异常，且重型 three 场景会显著增大首屏 HTML 体积与阻塞时间。`ssr:false` 的代价是增加一次客户端加载，收益是首屏即时呈现且 3D 仅在客户端执行。内容型站点中读者先看到页面、游戏随后加载，两者互不阻塞。

降级策略保留了 PCSS 软阴影。软阴影对空间感知贡献明显，清晰度下降对瞄准手感影响有限，因此默认保留阴影，仅在帧率持续下降时降低 dpr。

## 3. 渲染管线与性能自适应

Canvas 的几处配置需要说明：

```tsx
<Canvas flat shadows="percentage" camera={{ fov: 75, near: 0.1, far: 200 }}>
```

`flat` 关闭 three 的自动 tone mapping，全景图颜色按原始像素呈现。`shadows="percentage"` 启用百分比软阴影。透视相机 `fov` 为 75，远裁剪距离 200，足以覆盖训练场与天空球。

性能自适应在帧率持续下降时将 `gl.dpr` 降至 1，以清晰度换取帧率。移动端高分屏固定 `dpr=2~3` 容易掉帧，本项目用 drei 的 `<PerformanceMonitor>` 在 `onDecline` 回调中降低 DPR。

每帧可变状态与触发 React 渲染的 UI 状态应当分离，并在必要时对 dpr、阴影、抗锯齿做自动降级。

## 4. 状态管理：共享 store 与状态分层

`app/store.ts` 以 zustand 暴露单例 `useGame`，区分两类状态。

每帧高频变化的运行时状态（相机 `yaw`/`pitch`、位置、速度、`keys`、`locked`）在 `useFrame` 中直接写入，或由组件内的 `useRef` 持有并仅供 `useFrame` 读取，订阅者少，不会引起大规模重渲染。

低频、需要 DOM 立即反映的 UI 状态（`score`、`hits`、`shots`、`started`）由 DOM 层用选择器订阅，仅对应切片变化时重渲染该组件。

`Tuning` 是一份可调参数对象（`app/store.ts:149`），将背景、武器、网格、靶子、灵敏度全部数据化。拖动面板滑块触发 `setTuning(patch)` 并重新摆放存活靶子，无需刷新页面。

计分由纯函数 `computeScore`（`app/store.ts:121`）完成，使游戏数值与渲染代码解耦：

```ts
const edge = Math.min(1, Math.max(Math.abs(az) / t.arcA, Math.abs(el) / t.arcEmax));
const small = Math.min(
  1,
  Math.max(0, (t.targetSizeMax - size) / (t.targetSizeMax - t.targetSizeMin))
);
return Math.round(10 + edge * 5 + small * 5); // 范围约 10~20
```

公式化表达为：

<Math block>{`\\text{score}=\\left\\lfloor 10+5\\,e+5\\,s\\right\\rfloor,\\quad e=\\min\\!\\left(1,\\max\\!\\left(\\tfrac{|az|}{\\text{arc}_A},\\tfrac{|el|}{\\text{arc}_{E_{\\max}}}\\right)\\right),\\quad s=\\min\\!\\left(1,\\max\\!\\left(0,\\tfrac{\\text{size}_{\\max}-\\text{size}}{\\text{size}_{\\max}-\\text{size}_{\\min}}\\right)\\right)`}</Math>

分数范围约 10~20，边缘距离与尺寸共同决定难度权重。

### 4.1 选择依据：相机状态是否进入 React state

以 `useState` 保存 `yaw`/`pitch`/`position` 并每帧 `setState` 的写法，会使 React 在 60~144fps 下每帧重渲染整棵订阅树，开销不可接受。高频运行时状态作为命令式可变对象，与 React 声明式状态分离。相机朝向在 `useFrame` 中直接赋值，不经 React 协调层，性能与裸 three.js 一致；分数、命中数这类需要观察的状态才走 React 订阅。

`computeScore` 提取为纯函数后，计分规则可单测、可被策划直接阅读，无需深入射线逻辑。数值与渲染解耦是快速调参的前提。

## 5. 第一人称控制：Pointer Lock 与即时视角

`app/components/Player.tsx` 不渲染可见内容（`return null`），在 `useEffect` 中注册监听、在 `useFrame` 中每帧更新相机。

### 5.1 Pointer Lock：捕获鼠标增量

点击画面触发 `el.requestPointerLock()`。锁定后鼠标不受屏幕边缘限制，`mousemove` 事件提供 `movementX`/`movementY`（本次移动的像素增量）。

```ts
const onMove = (e: MouseEvent) => {
  if (document.pointerLockElement !== el) return;
  const sens = useGame.getState().tuning.lookSens;
  targetYaw.current   -= e.movementX * BASE_SENS * sens;
  targetPitch.current -= e.movementY * BASE_SENS * sens;
  targetPitch.current = THREE.MathUtils.clamp(targetPitch.current, -MAX_PITCH, MAX_PITCH);
};
```

`BASE_SENS = 0.0022` 弧度/像素为基准灵敏度，`lookSens` 为倍率。`yaw` 用 `-=` 计算，鼠标右移使视角右转；`pitch` 以 `clamp` 限制于 ±85°，避免翻转过头。

按 Esc 退出 Pointer Lock 后浏览器进入短暂冷却期，期间再次调用 `requestPointerLock` 会抛 `SecurityError` 或 reject Promise。代码以 `try/catch` 与 `p.catch(() => {})` 捕获该异常（`Player.tsx:55`），否则控制台会持续报错。

### 5.2 即时视角：准星、视线、子弹一致

```ts
useFrame((_, delta) => {
  if (!useGame.getState().started) return;
  camera.rotation.set(targetPitch.current, targetYaw.current, 0);
  camera.updateMatrixWorld();
  // ... WASD 移动
});
```

相机 `rotation.order = "YXZ"`（`Player.tsx:27`），先 yaw 后 pitch，可规避万向锁式抖动。`rotation.set(pitch, yaw, 0)` 每帧直接将目标视角赋给相机，无插值或阻尼。准星固定于屏幕中心，子弹沿中心射线发射，阻尼会使画面滞后于鼠标导致射线与准星错位。零延迟视角保证三者一致，是命中判定的前提。

### 5.3 WASD 移动：相对朝向、帧率无关

```ts
camera.getWorldDirection(dir.current);
dir.current.y = 0; dir.current.normalize();
rightVec.current.crossVectors(dir.current, camera.up).normalize();
move.current.multiplyScalar(2.5 * delta);
camera.position.add(move.current);
camera.position.y = 1.6;
camera.position.x = clamp(x, -25, 25);
camera.position.z = clamp(z, -28, 15);
```

`2.5 * delta` 使每帧位移乘以帧间隔，移动速度在 60fps 与 144fps 下一致。位置被限制于训练场范围内，`y` 锁死为 1.6（人眼高度），玩家只能平移。

### 5.4 选择依据：即时视角与帧率无关移动

视角即时、移动帧率无关方向相反。FPS 的硬性契约是准星即所见，零延迟视角是必要条件，阻尼平滑无法满足。移动不绑定视觉契约，玩家只关注位移距离，以 `delta` 归一化即可使不同帧率下位移一致。

`BASE_SENS` 以像素为单位，`delta` 不参与视角计算（代码注释标注「视角灵敏度用像素、不用 delta」）。`movementX` 本身是像素增量，与帧率无关，相乘后天然帧率无关；移动是每帧持续施加的位移，才需要 `delta`。两种物理量采用两套帧率无关策略，是按物理含义选型的结果。

移动速度 `2.5` 硬编码、未暴露给 `Tuning`。移动手感属于底层契约，调参面板仅面向视觉与靶子分布，不应由非程序员调整的量保持隐藏。

## 6. 靶子生成：角度空间抖动

### 6.1 问题：笛卡尔坐标抖动导致出界

靶子分布在以相机为球心、半径 R 的球面上（非平面网格）。在网格点附近按随机米数偏移生成靶子，球面边缘方向不一致，在 `x`/`y`/`z` 上 `position += random` 容易把靶子推出 `arcA`/`arcEmax` 边界，甚至穿出天花板或移到相机背后。

### 6.2 解法：在角度空间抖动

`SpawnGrid.genGridPositions`（`app/components/SpawnGrid.tsx:39`）生成一组固定角间距的参考点，边界由 `arcA`/`arcEmax`/`arcEmin` 定义。相邻点角度差恒为 `gridSpacing`；总跨度取 `min((n-1) * spacing, 边界范围)`；点阵居中且不超边界，因此改行列数只改变覆盖面积，不改变间距。

`store.ts` 中的 `randomPosWithSlot`（`app/store.ts:63`）执行一次坐标变换：

```ts
const idx = pickSlot()!;
const base = toAngles(c[0], c[1], c[2]);     // 世界 → (az, el)
const jAng = tuning.jitter / tuning.arcRadius;
let az = base.az + (Math.random() - 0.5) * jAng;
let el = base.el + (Math.random() - 0.5) * jAng * 0.4;
const margin = Math.atan(size / tuning.arcRadius);
az = clamp(az, -tuning.arcA + margin, tuning.arcA - margin);
el = clamp(el, -tuning.arcEmin + margin, tuning.arcEmax - margin);
return { pos: fromAngles(az, el, tuning.arcRadius), idx, size };
```

`toAngles`/`fromAngles` 是球面角与世界坐标的互转（`app/store.ts:31`）。边界 `arcA`/`arcEmax` 以弧度定义，将 jitter 换算为弧度并在角度空间 clamp，即可保证靶子落入合法弧面，与 jitter 取值无关：

<Math block>{`az\\in\\big[-\\text{arc}_A+m,\\;\\text{arc}_A-m\\big],\\quad el\\in\\big[-\\text{arc}_{E_{\\min}}+m,\\;\\text{arc}_{E_{\\max}}-m\\big],\\quad m=\\arctan\\!\\left(\\tfrac{\\text{size}}{R}\\right)`}</Math>

`m` 为靶子半径对应的角宽度安全边距。

### 6.3 槽位占用：避免重叠

`pickSlot`/`releaseSlot`（`app/components/SpawnGrid.tsx:76`）用 `Set<number>` 记录已占用槽位。生成时随机选取未占用槽位，命中后释放旧槽位并重新分配。同一时刻的 N 个靶子分布在不同参考点附近，不会重叠。

### 6.4 选择依据：角度空间抖动

在网格点附近叠加随机米数的方案中，球面几何使米数与角度呈非线性：越靠近边界，相同米数偏移对应的角度越大，出界概率越高，只能缩小 jitter 规避，靶子会聚集于中心。改用在弧度边界内 clamp 的角度坐标系后，出界问题从数学上消除，调参仅能压制。网格参考点同时解耦靶子覆盖面积与间距：调整行列数只改变覆盖、不改变密度。

槽位制的条件是 N 个靶子不超过槽位数，否则 `pickSlot()!` 会因无空位断言失败。当前训练场网格足够密集，该边界不会被触发，因此不为其构建复杂回退，用一个前提假设换取代码简洁。

## 7. 命中判定：屏幕中心射线

射击在 `Player.tsx` 的 `mousedown` 中完成：

```ts
const shoot = () => {
  const state = useGame.getState();
  if (!state.started) return;
  if (document.pointerLockElement !== gl.domElement) return;
  state.shoot();
  raycaster.current.setFromCamera(new THREE.Vector2(0, 0), camera);
  const meshes = getTargetMeshes().filter((m) => m.parent?.visible !== false);
  const hits = raycaster.current.intersectObjects(meshes, false);
  if (hits.length > 0) {
    const id = hits[0].object.userData.targetId as number;
    useGame.getState().hitTarget(id);
  }
};
```

`setFromCamera((0,0), camera)` 从屏幕中心发射射线，与准星、相机前向对齐，印证了即时视角的必要性。`getTargetMeshes()`（`app/lib/targets.ts`）是 mesh 注册表：每个靶球在 `ref` 回调中执行 `registerTarget(id, mesh)`（`app/components/Targets.tsx:15`），命中检测从注册表取全部 mesh 做射线相交，避免遍历 `scene.children` 误射环境。`userData.targetId` 用于反查命中 mesh 所属的靶子（`app/components/Targets.tsx:14`），再交 store 加分并重新摆放。

命中后 `hitTarget(id)`（`app/store.ts:284`）执行算分、加分、释放旧槽位、重新分配位置，构成无限训练循环。

## 8. 调参面板：把参数数据化

`app/components/TuningPanel.tsx` 将所有参数组织为分组滑块（背景、武器、网格、靶子、视角）。拖动触发 `setTuning` 并实时 `refreshTargets`。复制参数 JSON 将整份 `Tuning` 写入剪贴板，可直接交付工程写入 `DEFAULT_TUNING`，使美术与策划的调整与工程代码分离。

### 8.1 选择依据：复制 JSON 而非预设系统

预设下拉框（flick、tracking、micro）或后端配置属于更重的方案。本项目采用一份 `Tuning` 对象加一个复制按钮，依据有三点。`Tuning` 已是纯数据，复制出的 JSON 即视觉规格书，策划与工程之间无需另设描述语言。预设系统需要维护命名、版本、默认值迁移，在模式种类未确定前建立系统会成为负债。面板 `reset` 可恢复默认，复制 JSON 负责前进、reset 负责后退，闭环已足够。

复制粘贴一段 JSON 即可解决问题时，不必优先构建配置中心。出现第二、第三种固定模式后再沉淀为预设，`Tuning` 的形状已稳定，抽象成本更低。

## 9. 主线：把约束放到正确的抽象层

前述决策有一条共同主线。出界问题因边界以弧度定义，在角度坐标系内由弧度 clamp 消除。每帧重渲染通过将高频状态移出 React、走命令式解决，性能与裸 three.js 一致。准星与子弹错位通过保持视角零延迟（无阻尼）解决。调参协作通过令 `Tuning` 数据结构直接作为策划与工程的接口解决，省去专有描述语言。

问题反复出现时，优先核查其所在的抽象层是否恰当。坐标系、状态层、渲染层、协作层选对层级，许多难题会自然消解。
