# AI 原生公司：以目标、能力与实验重构组织


当生产力与人数解绑之后，公司按什么单位来组织？

## 为什么要重看公司组织形式

过去约一百年，公司组织设计默认一条假设：**人是生产力的基本单位**。

职位、部门、管理层、流程与 KPI，都建立在这条假设上。增长路径通常写成两件事：增加员工数量，提高单人效率。规模也习惯用人数衡量——十人、千人、万人——这是工业时代留下的度量。

AI 正在改写这条前提。小团队配合模型与工具，已能覆盖市场研究、内容生产、软件开发、客户支持、数据分析、销售触达等过去需要更大编制才能完成的工作。

于是问题变成：**若产出不再随人数近似线性扩展，组织应以何种单位重新设计？**

「AI-native Company」（AI 原生公司）讨论的，正是这一层。

## 传统公司的瓶颈在协调

一千人规模的公司，常见链条是：CEO → VP → Director → Manager → Employee。决策沿链下传，信息逐级损耗，响应变慢，部门之间形成壁垒，同类工作被重复。编制扩大后，管理开销往往同步上升。

以营销需求为例，传统链路常是：提出目标 → 市场制定计划 → 内容写方案 → 设计出素材 → 投放 → 数据分析 → 复盘。走完一轮，经常以周计。

真正紧缺的，是一套能理解目标、拆解问题、并根据结果持续调整的**智能协调系统**。

## OpenAI 与 Anthropic 的组织线索

一种常见想象是「CEO + 一百个 AI 员工」。公开信息里，OpenAI、Anthropic 仍然有人、有汇报线、有产品与工程编制；可观察的重点是：**工作如何跨研究与产品闭环**，以及**研究侧如何按问题域切开**。下面分开说编制事实与可抽取的启发，避免把研究标签误当成整家公司的组织表。

### OpenAI：研究与应用分家，产品靠端到端小队

编制层面，OpenAI 大致是双轨：一边做前沿模型研究（训练、评测、安全阈值），一边做应用与商业化（ChatGPT、API、企业交付）。工程侧常见切法是：

- **水平团队（horizontal）**：共享基础设施，例如训练/推理平台、实时语音与 RTC 等，服务多条产品线
- **垂直团队（vertical）**：围绕具体体验与指标，例如核心对话体验、高阶用户场景，对结果负责

产品怎么做出来：模型能力在研究侧迭代；落到 ChatGPT / API 时，由研究、工程、产品、设计组成的端到端小队一起推进。公开访谈里常强调 **DRI（Directly Responsible Individual）**：一个人对整条结果负责，缩短「研究出模型 → 产品可用」的链路。落地方式是**人组小队 + 共享平台 + 快速实验**把模型能力产品化；这与「一百个 AI 员工自动生成产品」的想象相距甚远。

从能力视角抽象，仍可看到三类工作持续交织：

- **Research**：模型能力、推理、对齐与安全评测
- **Engineering**：训练与推理基础设施、服务可靠性
- **Product**：需求、体验、增长与商业化

它们共享同一套模型与算力平台，跨小队调用；这是「能力组合」层面的观察，不等于公司已经取消部门编制。

### Anthropic：研究按问题域切开，产品仍是 Claude 交付链

Anthropic 对外更常以「AI safety company」自居。官网公开的研究团队按**问题域**划分，例如 Alignment、Interpretability、Societal Impacts、Frontier Red Team、Economic Research 等——对齐、可解释、红队与社会影响各自成队，主线是弄清并约束高能力模型的行为。

这几项描述的是**研究侧怎么切题**，不是公司只剩这几块。Claude.ai 与 Claude API 仍然需要产品、应用工程、基础设施、政策与商业化去交付：训练与对齐产出模型行为；产品与工程把它接到对话产品、工具调用与企业场景；安全与评测贯穿发布前后。Claude 既是商品，也常被当作可观察的研究载体——部署本身带有「安全技术在规模下是否站得住」的检验意味。

因此：OpenAI 公开叙事更偏「研究 / 应用 / 产品功能」如何协作；Anthropic 公开研究叙事更偏「安全相关问题域」如何并行推进。两者都有完整的产品交付链；差异主要在研究侧的切题方式，以及产品与安全约束如何绑在一起。

### 能抽出什么，抽不出什么

抽得出的是工作环路：**目标（或基准 / 产品指标）→ 多类能力并行实验 → 评估与反馈 → 再分配下一轮探索**。例如抬高某项基准：研究侧提出候选方法，工程侧做成可对比实验，评估与安全给出成绩与风险；优者放大、劣者淘汰，结果再改写下一轮研究方向。产品侧同理：体验指标驱动小队实验，共享平台承接流量与推理。

抽不出的是「它们已经按 Capability 取代了全部部门」。编制仍在；启发在于——**一级协调对象可以是目标与能力组合，岗位表退居实现细节**。后文说的 AI-native Company，是把这一层显式做成操作系统；讨论范围是系统设计，不含复述某家公司的内部通讯录。

## 重新定义基本运作单位

传统公司的基本单位可写成：Employee → Task → Result。

AI 原生公司更贴近：Goal → Capability → Experiment → Result。

为何不宜直接套「AI 员工」？

「员工」概念携带固定职位、固定职责、固定技能边界。模型与工具不需要按工位锁定。

以增长目标「提升产品用户量」为例，需要的是能力组合：Research 找需求，Writing 产内容，Video 做素材，Browser 执行运营动作，Analytics 读结果。能力按目标动态编排；固定职位描述反而成为约束。

## 核心模型：从使命到工具的链路

一条可操作的结构链是：

**Mission → Goal → Strategy → Experiment → Task → Capability → Tool**

- **Mission（使命）**：存在理由，例如「帮助一百万人学习 AI」
- **Goal（目标）**：可度量结果，例如「一年达到一百万用户」
- **Strategy（策略）**：实现路径，例如内容增长、社区增长、产品增长
- **Experiment（实验）**：并行试探有效方法的单位。同一增长目标下，可同时试验 Twitter 运营、短视频、SEO、邮件等多条路径
- **Evaluation（评估）**：独立于执行的度量系统。若目标是「增加用户」，却用「发布一百条内容」当 KPI，系统会优化到产量；应回到新增用户、转化率、ROI 等结果指标

其中 Experiment 与 Evaluation 成对出现：没有评估，实验只会放大噪声。

## 组织结构：四层叠放

职能式切分（市场 / 研发 / 销售）之外，更贴近 AI 原生运作的是分层：

**Mission Layer → Strategy Layer → Capability Platform → Execution Layer**

- **Capability Platform（能力平台）**：Research、Writing、Coding、Design、Video、Browser、Analytics、Sales 等模块，类似可调度的内部能力总线
- **Execution Layer（执行层）**：对接 Twitter、TikTok、YouTube、GitHub、邮件、CRM 等外部系统，对应链路中的 Tool

上层定义「做什么、为何做」；能力平台回答「谁能做」；执行层回答「在哪里做」。

## AIOS：十人编制调度千人级能力

优先建设的是 **AI Organization Operating System**（AIOS），用来调度能力与实验；堆砌一千个 Agent 分身本身解决不了协调问题。

AIOS 至少承担五件事：

1. **Goal Management（目标管理）**：解析目标，例如「今年增长十倍」
2. **Planning（规划）**：拆成流量、转化、留存等子问题
3. **Capability Scheduling（能力调度）**：按需调用 Writing、Video 等能力
4. **Execution（执行）**：由 Browser Agent 等完成打开发布、采集数据等动作
5. **Evaluation（评估）**：比较方案效果并加大投入有效路径。例如方案 A 与 B 同等投入下分别带来 20 与 500 名用户，系统应提高 B 的资源权重

## 护城河：可复制的是 Agent，难复制的是资产

Agent 与提示词容易被复制。更稳固的壁垒通常落在：

1. **Knowledge（知识）**：产品、用户、市场的专有知识
2. **Memory（记忆）**：组织经验，例如历史实验记录
3. **Capability（能力）**：内容、设计、销售等已组织化的能力模块
4. **Evaluation（评估）**：辨别「什么真正有效」的度量与判断
5. **Experiment History（实验历史）**：做过什么、因何失败的可检索档案

竞争焦点从「谁有更多 Agent」转到「谁积累了更厚的目标—能力—实验闭环资产」。

## 第一阶段：先闭合一条增长环

不必一次性建成完整「AI Company」。更稳妥的路径是先验证一条闭环。

可从 **AI Growth Company** 切入：用户输入目标 → 生成增长计划 → 发现机会 → 生成内容 → 人工确认 → 自动发布 → 回收数据 → 调整策略。

该闭环稳定之后，再向营销、软件交付、销售、媒体等垂直形态扩展。

## 结语

过去常用公式：公司 = 人 × 流程。

更贴近 AI 原生形态的写法是：公司 = **目标 × 能力 × 学习循环**。

工业时代组织人力，互联网时代组织信息流。下一阶段要组织的，是可调度的智能能力：目标理解、能力调度与持续学习。这就是 AI-native Company 的核心。
