# 推理优化：让模型跑得更快

<SeriesNav series="llm" />

一个 7B 模型推理一次，FP16 精度需要 14GB 显存。生成 100 个 token 需要几秒。如果要服务 100 个并发用户？1400GB 显存 + 几分钟延迟。不可接受。

这篇讲三个核心优化：量化（减小模型体积）、Speculative Decoding（加速生成）、Continuous Batching（提升吞吐）。

---

## 量化：用更少的 bit 存权重

FP32 → FP16 → INT8 → INT4，精度递减但体积大幅缩小：

```text
LLaMA-7B 模型大小:
  FP32:  28 GB
  FP16:  14 GB    (2x 压缩，几乎无损)
  INT8:   7 GB    (4x 压缩，微小损失)
  INT4:  3.5 GB   (8x 压缩，轻微损失)
```

INT4 的 7B 模型只需要 3.5GB 显存——一张消费级显卡就能跑。

### 为什么能量化

模型权重的分布很集中——大部分值在 [-0.1, 0.1] 之间，极少有很大的值。用 4 bit 也能表示这个范围内的值，只是精度粗了一点。

### 主流方法

| 方法 | 特点 |
|------|------|
| GPTQ | 逐层量化，需要校准数据，离线完成 |
| AWQ | 保护重要权重通道不量化 |
| GGUF | llama.cpp 格式，CPU 也能跑 |
| bitsandbytes | 动态量化，HuggingFace 集成 |

---

## Speculative Decoding：用小模型加速大模型

大模型自回归生成慢的原因：每个 token 都要过完整的几十层。但大部分 token 其实"很好猜"——"The capital of France is" 后面大概率是 "Paris"。

思路：
1. 用一个**小模型**（draft model）快速猜 K 个 token
2. 用大模型**一次性验证**这 K 个 token
3. 如果猜对了，直接用；猜错的那个位置重新生成

```text
小模型猜: ["Paris", ".", " It", " is", " known"]  (5 个 token, 很快)
大模型验: [✓, ✓, ✓, ✓, ✗]                       (1 次前向, 确认前 4 个对了)
→ 相当于大模型 1 次前向就生成了 4 个 token（正常要 4 次）
```

加速比取决于小模型猜对的比例。通常能加速 2-3x。

---

## Continuous Batching：多请求共享算力

传统 batching：等 N 个请求凑齐，一起做前向。问题是长请求拖慢短请求。

Continuous batching：
- 短请求结束了立刻让新请求进来
- 每一步只给"还在生成的"请求做前向
- 不同请求可以有不同长度

vLLM 的 PagedAttention 进一步优化：KV Cache 不再连续存储，而是像操作系统的虚拟内存一样分页管理，减少碎片浪费。

---

## 效果汇总

| 优化 | 效果 | 代价 |
|------|------|------|
| FP16 → INT4 量化 | 显存 4x↓ | 质量微降 |
| KV Cache (上篇) | 速度 ~10x↑ | 显存换速度 |
| GQA (上篇) | KV 显存 2-8x↓ | — |
| Speculative Decoding | 速度 2-3x↑ | 需要小模型 |
| Continuous Batching | 吞吐 2-4x↑ | 实现复杂 |
| Flash Attention | 速度 2-4x↑ + 显存↓ | 需要 CUDA |

组合起来：INT4 量化 + KV Cache + GQA + Continuous Batching = 一张 A100 服务几十个并发用户。
