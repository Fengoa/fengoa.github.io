# 推理优化：提升推理速度

<SeriesNav series="llm" />

一个 7B 模型推理一次，FP16 精度要 14 GB 显存，生成 100 个 token 需等待数秒。若同时服务 100 个用户，按此配置需约 1400 GB 显存并产生数分钟延迟，系统难以承载。

模型训练完成并部署后，真正耗时的是这一段。这篇主要拆三个东西：把模型压小（量化）、让生成本身更快（投机解码）、把多个请求挤在一起（连续批处理）。

<QuantizationBits />

## 量化：用更少的位数存权重

把每个权重原本用 32 位浮点存的值，改成 16 位、8 位甚至 4 位整数。位数减半，模型体积同步缩减。LLaMA-7B 在 FP16 下为 14 GB，INT4 量化后仅 3.5 GB，可部署至消费级显卡。

机制类似图像压缩。一组浮点权重 `w`，量化的核心是把它们映射到 `q` 个整数格子上：

<Math block>{`q = \\text{round}\\!\\left(\\frac{w - z}{s}\\right), \\quad \\hat{w} = s \\cdot q + z`}</Math>

`s` 是 scale，`z` 是 zero-point。挑一个范围，等分成 16 格（INT4）或 256 格（INT8），每个权重落到最近的格子上。还原的时候只是把整数乘回 scale。

误差从哪来？落点不可能正好落在格点上，需四舍五入到最近格点。位数越少，相邻格点间隔越大，误差也越大。只要权重分布足够集中，该误差通常可接受。

### 为什么量化能成

模型权重不是均匀散布在 `[-1, 1]`。绝大部分会挤在 `0` 附近的窄带里，远端只有零星几个。直接把整段 `[-1, 1]` 切成 16 格太亏——大部分格子根本用不上。

<WeightDistributionHistogram />

实际做法是先看一遍权重的分布，挑一个合适的截断范围（比如 `±0.1`），把这段切 16 份。落在范围外的少数权重直接饱和到边界——损失一点尾部精度，换来对主体的精细分辨。

GPTQ、AWQ、bitsandbytes 等工具本质相同，差异在于校准数据用量、重要通道保护策略及量化后是否微调修复。GGUF 为 llama.cpp 存储格式，适用于 CPU 推理。

| 方法 | 关键做法 | 用在哪 |
|------|---------|--------|
| GPTQ | 离线，按层做误差最小化 | 生产部署，质量最稳 |
| AWQ | 保护 1% 关键通道不量化 | LLaMA 生态主流 |
| bitsandbytes | 推理时动态量化 | HuggingFace 一键加载 |
| GGUF | llama.cpp 的格式 | 本地、CPU、边缘设备 |

## 投机解码：让小模型先猜

大模型每生成一个 token 都要把几十层走一遍。但很多 token 其实非常好猜——「The capital of France is」后面几乎肯定是「Paris」。这种地方让大模型从头算一遍，纯属浪费。

思路是引入一个小模型作为起草器（draft model）。小模型每步仅需一两毫秒，可连续预测 4 个 token；大模型将这 4 个 token 拼接后，**一次** forward 同时验证全部四个。猜中部分直接采用，遇到第一个不一致位置时以大模型输出替换并停止，下一轮再开始。

<SpeculativeDecodingFlow />

加速比看小模型猜对的比例。在常见对话场景下能稳定拿到 2-3×。如果开始处理代码生成、专业术语之类小模型不熟的内容，命中率会掉，加速也会缩水。

Medusa 和 EAGLE 是这个思路的延伸——在大模型上接几个轻量的预测头，直接让大模型自己「猜自己下一步」，工程上更省事，无需单独训练一个小模型。

## 连续批处理：把空闲算力填满

GPU 执行 batch size = 1 与 batch size = 16 耗时相近，因算力本身支持大规模并行。服务端将多用户请求合并为 batch，单次前向通过模型，各用户分摊时间相应减少。

但传统做法的问题是 batch 必须等到最长那个请求结束才能换。短请求早早算完了也得空等，新来的请求只能在外面排队。

连续批处理的做法是把 batch 看成一个动态的池子。每生成一个 token 都重新组装一次：谁结束了就把槽位让出来，外面排队的立刻进来填上，不浪费任何一步。

<ContinuousBatchingTimeline />

vLLM 在此之上又加了 PagedAttention。问题在于 KV Cache——每个请求生成时都在累积一段缓存，长度不固定。如果按最长长度预留连续显存，会出现大量碎片。PagedAttention 把 KV Cache 切成小块（页），按需分配，跟操作系统管理虚拟内存是一个套路。结果是单卡能塞下的并发请求数翻倍。

## 延迟和吞吐之间的权衡

batch 越大、吞吐越高，但每个请求等的时间也越长。这是一道典型的取舍题。

<LatencyThroughputTradeoff />

`bs=1` 时单条延迟最低，但 GPU 大部分时间为空闲；`bs=64` 将硬件利用率拉满，吞吐达到峰值，但用户需等待更久才看到首字。实际部署需按场景取舍：聊天应用看重首 token 延迟（TTFT），偏向小 batch；离线评测、批量摘要可将 batch 开至较大。

vLLM 默认的 continuous batching 已较好平衡该权衡：新请求随时入队、长请求不拖累短请求，单卡可在延迟与吞吐间取得较优平衡。
