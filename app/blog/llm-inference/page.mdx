# 推理优化：让模型跑得更快

<SeriesNav series="llm" />

一个 7B 模型推理一次，FP16 精度要 14 GB 显存，生成 100 个 token 要等几秒。如果同时来 100 个用户，按这个跑法就是 1400 GB 显存加上几分钟延迟，谁也撑不住。

模型训完上线后真正花时间的就是这一段。这篇主要拆三个东西：把模型压小（量化）、让生成本身更快（投机解码）、把多个请求挤在一起（连续批处理）。

<QuantizationBits />

## 量化：用更少的位数存权重

把每个权重原本用 32 位浮点存的值，改成 16 位、8 位甚至 4 位整数。位数砍半，模型体积也跟着砍半。LLaMA-7B 在 FP16 下是 14 GB，换成 INT4 只剩 3.5 GB，刚好能塞进消费级显卡。

听起来像在压缩图片，本质也差不多。一组浮点权重 `w`，量化的核心是把它们映射到 `q` 个整数格子上：

<Math block>{`q = \\text{round}\\!\\left(\\frac{w - z}{s}\\right), \\quad \\hat{w} = s \\cdot q + z`}</Math>

`s` 是 scale，`z` 是 zero-point。挑一个范围，等分成 16 格（INT4）或 256 格（INT8），每个权重落到最近的格子上。还原的时候只是把整数乘回 scale。

误差从哪来？落点不可能正好踩在格子上，要四舍五入到最近的那个。所以位数越少，相邻格子的间隔越大，误差也越大。但只要权重本身的分布够集中，这个误差就还能接受。

### 为什么量化能成

模型权重不是均匀散布在 `[-1, 1]`。绝大部分会挤在 `0` 附近的窄带里，远端只有零星几个。直接把整段 `[-1, 1]` 切成 16 格太亏——大部分格子根本用不上。

<WeightDistributionHistogram />

实际做法是先看一遍权重的分布，挑一个合适的截断范围（比如 `±0.1`），把这段切 16 份。落在范围外的少数权重直接饱和到边界——损失一点尾部精度，换来对主体的精细分辨。

GPTQ、AWQ、bitsandbytes 这些工具本质都在做同一件事，区别在用多少校准数据、是否保护重要通道、量化后还要不要做微调修复。GGUF 是 llama.cpp 的存储格式，方便 CPU 跑。

| 方法 | 关键做法 | 用在哪 |
|------|---------|--------|
| GPTQ | 离线，按层做误差最小化 | 生产部署，质量最稳 |
| AWQ | 保护 1% 关键通道不量化 | LLaMA 生态主流 |
| bitsandbytes | 推理时动态量化 | HuggingFace 一键加载 |
| GGUF | llama.cpp 的格式 | 本地、CPU、边缘设备 |

## 投机解码：让小模型先猜

大模型每生成一个 token 都要把几十层走一遍。但很多 token 其实非常好猜——「The capital of France is」后面几乎肯定是「Paris」。这种地方让大模型从头算一遍，纯属浪费。

思路是拉一个小模型来当陪跑。小模型每步只用一两毫秒，先一口气猜出 4 个 token；大模型把这 4 个 token 拼回去，**一次** forward 就能同时验证全部四个。猜中的部分直接采用，遇到第一个不一致的位置，用大模型自己的输出替换并停下，下一轮再开始。

<SpeculativeDecodingFlow />

加速比看小模型猜对的比例。在常见对话场景下能稳定拿到 2-3×。如果开始处理代码生成、专业术语之类小模型不熟的内容，命中率会掉，加速也会缩水。

Medusa 和 EAGLE 是这个思路的延伸——不再单独训练一个小模型，而是在大模型上接几个轻量的预测头，直接让大模型自己「猜自己下一步」，工程上更省事。

## 连续批处理：把空闲算力填满

GPU 这种东西，跑 batch size = 1 和跑 batch size = 16 花的时间差不多，因为算力本来就是一次能并行算很多。所以服务端把多个用户请求拼成一个 batch，一次过模型，算下来每个用户分摊的时间就少了。

但传统做法的问题是 batch 必须等到最长那个请求结束才能换。短请求早早算完了也得空等，新来的请求只能在外面排队。

连续批处理的做法是把 batch 看成一个动态的池子。每生成一个 token 都重新组装一次：谁结束了就把槽位让出来，外面排队的立刻进来填上，不浪费任何一步。

<ContinuousBatchingTimeline />

vLLM 在此之上又加了 PagedAttention。问题在于 KV Cache——每个请求生成时都在累积一段缓存，长度不固定。如果按最长长度预留连续显存，会出现大量碎片。PagedAttention 把 KV Cache 切成小块（页），按需分配，跟操作系统管理虚拟内存是一个套路。结果是单卡能塞下的并发请求数翻倍。

## 延迟和吞吐之间的权衡

batch 越大、吞吐越高，但每个请求等的时间也越长。这是一道典型的取舍题。

<LatencyThroughputTradeoff />

`bs=1` 时单条延迟最低，但 GPU 大半时间在闲；`bs=64` 把硬件榨满，吞吐拉到最高，但用户得等更久才看到第一个字。实际部署时要看场景：聊天应用看重首 token 延迟（TTFT），偏向小 batch；离线评测、批量摘要这种则可以一把梭，把 batch 开到顶。

vLLM 默认的 continuous batching 已经把这件事做得相当聪明，新请求随时进队、长请求不会拖累短请求，单卡能把延迟和吞吐同时拉到比较舒服的位置。
