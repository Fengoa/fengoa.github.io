# 从零搭建一个推荐系统

<SeriesNav series="recsys" />

打开 Spotify，首页推荐了一首未曾听过的歌曲，播放后发现颇为符合个人口味。该推荐系统是如何判断用户偏好的？

这一问题可拆解为两个子问题：

1. 曲库中包含一亿首歌曲，为何仅有这 30 首被推荐？
2. 在这 30 首推荐歌曲中，为何此歌曲排名第一？

第二个问题相对简单——计算得分并排序即可。第一个问题才是核心难点：一亿首歌曲无法逐一打分，计算时间不允许。

因此工业界采用两阶段架构。第一阶段称为**召回**，利用简单规则快速筛选一批候选，目标是以高召回率为优先级；第二阶段称为**排序**，引入更丰富的特征信号进行精确打分，将最匹配的条目排在前列，目标是以高精度为优先级。召回阶段追求速度，排序阶段追求准确性。

本文记录从零搭建一套此类推荐流水线的过程。数据采用 MovieLens，技术栈为 Python + FastAPI。


## 问题定义

推荐系统的任务可形式化为：

给用户 <Math>{`u`}</Math>，在所有物品 <Math>{`i`}</Math> 中，找到得分最高的 Top <Math>{`K`}</Math>：

<Math block>{`\\operatorname{score}(u, i) \\rightarrow \\text{排序} \\rightarrow \\text{Top } K`}</Math>

物品数量较大时，逐一算分不可行。工业界采用两阶段方案：先利用简单规则快速筛选数百个候选（召回），再对这数百个候选采用更复杂的方式精确打分（排序）。

## 召回：三路并行

召回的目标是从全量物品中快速筛选一批候选。单一策略存在覆盖盲区，因此采用三路并行策略，各取 40 部候选，最终合并去重至约 50 部：

```text
多路召回（各取 40 部候选）
  ├─ 热门召回        → 评分人数多 + 均分高的电影
  ├─ 类型偏好召回    → 用户常看类型的高分电影
  └─ ItemCF 召回    → 协同过滤相似电影
```

<RecallParallel />

### 热门召回

筛选评分人数多且均分高的电影。该方法不依赖用户历史，适用于新用户。其核心假设为：若多数用户评价较高，则当前用户也可能偏好该物品。

### 类型偏好召回

统计用户历史观看电影的类型分布，按频率计算权重。例如用户观看了 7 部 Drama 和 3 部 Comedy，则 Drama 权重为 0.7，Comedy 权重为 0.3。随后从对应类型中按权重选取高分电影。

### ItemCF 召回

其核心思路为：若用户喜欢物品 A，且物品 A 与物品 B 相似，则向该用户推荐物品 B。

具体实现为：离线遍历所有用户行为，统计物品间的共现关系，计算每个物品的相似物品列表。在线服务时仅需查表，无需实时计算。

需注意一个技术细节：活跃用户观看了数百部电影，若不加处理将导致所有物品两两相似。因此需采用 IUF 加权，即观看数量越多的用户，其每次共现的贡献度越低：

<Math block>{`\\text{weight} = \\frac{1}{\\log(1 + \\text{用户看过的电影数})}`}</Math>

此方法与搜索引擎中的 IDF 原理相近。

## 合并：归一化

三路召回各自返回候选及分数，但分数尺度存在差异：

```text
热门召回：recall_score = 评分人数（几十到几千）
类型召回：recall_score = 类型权重 × 均分（0 到 10）
ItemCF：  recall_score = 相似度累加（0 到 几）
```

由于量纲不同，直接相加无意义。需先归一化至 [0, 1] 区间：

```text
normalized = (score - min) / (max - min)
```

随后按权重合并各路召回结果。由于 ItemCF 具备最强的个性化特征，赋予其最高权重；热门召回泛化能力最强，权重最低：

```text
merged_score = 0.5 × itemcf_norm + 0.3 × genre_norm + 0.2 × popular_norm
```

合并完成后移除用户已观看的电影，输出候选集进入下一环节。

## 排序：引入物品质量信号

召回阶段仅考虑"该电影与用户是否相关"，未评估电影本身的质量。一部符合用户口味但评分仅为 3 分的低质电影不应排在前列。

排序阶段引入物品质量信号，不仅考虑召回分数，还评估该电影本身是否值得推荐：

```text
final_score = 0.5 × recall_score_norm    （召回置信度）
            + 0.3 × avg_rating_norm      （用户评分质量）
            + 0.2 × popularity_norm      （多少人看过）
```

精排前后的排名变化如下：

| 电影 | 召回排名 | 精排后 | 原因 |
|------|---------|--------|------|
| Raiders of the Lost Ark | 1 | 2 | 召回分最高，但质量信号不如肖申克 |
| Shawshank Redemption | 2 | 1 | 评分 9.1 + 310 万人评 |
| Godfather: Part II | 未进前 5 | 5 | 评分 8.7 + 210 万人评，热度补位 |

## 项目结构

完整实现后的项目结构如下：

```text
recommender/
  loader.py       # 数据加载，统一 ID 类型
  recall.py       # 三路召回 + 归一化合并
  ranker.py       # 精排打分
main.py           # FastAPI，对外暴露 /recommendations
scripts/
  build_itemcf.py # 离线构建 ItemCF 相似表
```

最终接口设计简洁，单个 GET 请求即可完成调用：

```text
GET /recommendations?user_id=1&top_k=20

→ 内部流程：
  popular_recall(40) ─┐
  genre_recall(40)   ─┼→ 归一化合并(50) → rank_candidates → Top 20
  itemcf_recall(40)  ─┘
```


## 与工业级系统的差距

本项目是一个完整但精简的推荐系统，与工业级应用的差距主要在规模和精度，两者结构相似：

| 环节 | 本项目 | 工业级应用 |
|------|---------|--------|
| 数据 | MovieLens pkl 文件 | 数据仓库 + 实时日志流 |
| 召回 | popular + genre + ItemCF | 同 + 向量召回 + DNN 召回 |
| 排序 | 手写线性公式 | DeepFM / DIN / Wide&Deep |
| 服务 | FastAPI + pandas 内存 | gRPC + Redis + 微服务 |

后续文章将添加向量召回，利用 embedding 进行语义匹配，进一步提升召回能力。
