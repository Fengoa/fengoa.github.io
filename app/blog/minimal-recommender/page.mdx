# 从零搭建一个推荐系统

<SeriesNav series="recsys" />

打开 Spotify 时，首页可能出现一首从未听过的歌曲，播放后发现与个人口味颇为契合。推荐系统是如何推断用户偏好的？

这一问题可拆成两个子问题：

1. 曲库规模达到一亿首，为何最终只推荐其中 30 首？
2. 在这 30 首里，为何某一首排在第一位？

第二个问题只需计算得分并排序。第一个问题更难：一亿首歌曲无法逐条打分，时间成本不允许。

工业界因此采用两阶段架构。第一阶段为**召回**：用简单规则快速筛出一批候选，优先保证召回率；第二阶段为**排序**：引入更丰富的特征做精确打分，把最匹配的条目排在前面，优先保证精度。召回求速度，排序求准确。

本文记录从零搭建此类推荐流水线的过程，数据使用 MovieLens，技术栈为 Python + FastAPI。

## 问题定义

推荐系统的任务可形式化为：

给用户 <Math>{`u`}</Math>，在所有物品 <Math>{`i`}</Math> 中，找到得分最高的 Top <Math>{`K`}</Math>：

<Math
  block
>{`\\operatorname{score}(u, i) \\rightarrow \\text{排序} \\rightarrow \\text{Top } K`}</Math>

物品规模较大时，逐条算分不可行，需先以简单规则快速筛出数百个候选（**召回**），再对这数百个候选做更精细的打分（**排序**）。

<RecommenderPipeline />

## 召回：三路并行

召回目标是从全量物品中快速筛出候选集。单一策略存在覆盖盲区，因此**三路并行**，各取 40 部，合并去重后约 50 部：

```text
多路召回（各取 40 部候选）
  ├─ 热门召回        → 评分人数多 + 均分高的电影
  ├─ 类型偏好召回    → 用户常看类型的高分电影
  └─ ItemCF 召回    → 协同过滤相似电影
```

<RecallParallel />

上图中三路召回并行执行，彼此独立、互不依赖。以下分别说明各路逻辑。

### 热门召回

热门召回不引入用户信息，仅依据电影自身的评分统计排序。**冷启动**场景下系统尚无行为数据，这一路把已被大量用户验证的影片优先送入候选集。

热度分定义为 **评分人数 × 均分**。下表用三部电影对比不同组合下的排序结果：

<PopularRecallScore />

「冷门佳作」均分 4.5 最高，但仅有 500 条评分，热度分排在最后。单看均分会放大小样本波动：十人给出的满分与三千人的高分不可等同，因此评分人数一并参与计分。

这一路对所有用户输出同一批候选，不做个性化。类型偏好与 ItemCF 分别从用户历史和物品相似性两个方向补足缺口。

### 类型偏好召回

类型偏好召回从用户历史出发：先统计观影记录中的类型分布，再在各类型内选取高分影片。

按观看次数计算各类型占比，并据此分配候选名额。例如某用户共看过 10 部，其中剧情 7 部、喜剧 3 部，则剧情权重 0.7、喜剧权重 0.3。每路召回取 40 个候选时，剧情分配 <Math>{`\\lfloor 40 \\times 0.7 \\rfloor = 28`}</Math> 个名额，喜剧分配 <Math>{`\\lfloor 40 \\times 0.3 \\rfloor = 12`}</Math> 个；各类型内部按评分从高到低选取。

下方动画按四个阶段展示完整流程；鼠标悬停顶部步骤标签可跳转查看对应阶段：

<GenreRecallFlow />

类型权重在**离线**阶段按用户预计算并持久化，**在线**请求直接查表取值。被选中影片的召回分等于该类型权重与影片均分的乘积：

<Math block>{`\\text{recall\\_score} = w_i \\times \\text{均分}`}</Math>

用户在某一类型上的观看次数越多，<Math>{`w_i`}</Math> 越大，该类型下影片的召回分随之升高。

纯新用户没有历史记录，各类型计数为零、权重亦为零，这一路返回空列表，由热门召回在合并阶段兜底。

### ItemCF 召回

ItemCF 的思路是：用户喜欢物品 A，且 A 与 B 相似，则向该用户推荐 B。

实现上分为**离线**与**在线**两阶段：离线遍历用户行为，统计物品共现关系，为每件物品预计算相似列表；在线请求只查表，不做实时计算。

有一个需要处理的细节：活跃用户可能看过数百部电影，若不降权，共现会把大量物品拉成「两两相似」。因此采用 **IUF 加权**，观影数越多的用户，单次共现贡献越低：

<Math
  block
>{`\\text{weight} = \\frac{1}{\\log(1 + \\text{用户看过的电影数})}`}</Math>

该方法与搜索引擎中的 IDF 思路相近。

## 合并：归一化

三路召回各返候选及分数，但**量纲**不同，不能直接相加：

- 热门召回：recall_score = 评分人数（几十到几千）
- 类型召回：recall_score = 类型权重 × 均分（0 到 10）
- ItemCF：recall_score = 相似度累加（0 到 几）

以《黑暗骑士》为例：热门召回 2900，类型召回 6.5，ItemCF 2.1。若直接相加，热门仍占绝对主导。归一化后三路分别为 0.89、0.00、0.80，才落到同一刻度，可以按权重合并。

每一路独立**归一化**到 [0, 1] 区间：该路最低记为 0，最高记为 1，其余按相对位置落在中间。

<Math block>{`\\text{norm} = \\frac{\\text{score} - \\min}{\\max - \\min}`}</Math>

再按权重合并。**ItemCF** 个性化最强，权重最高；**热门召回** 泛化最广，权重最低：

<Math block>{`\\begin{aligned}
\\text{merged\\_score} &= 0.5 \\times \\text{itemcf\\_norm} \\\\
&\\quad + \\; 0.3 \\times \\text{genre\\_norm} \\\\
&\\quad + \\; 0.2 \\times \\text{popular\\_norm}
\\end{aligned}`}</Math>

其中 `itemcf_norm`、`genre_norm`、`popular_norm` 为三路分数各自归一化后的值，与上图动画第三步一致。

合并后剔除用户已观看的电影，候选集进入排序环节。

## 排序：引入物品质量信号

召回只回答「这部电影与该用户是否相关」，未衡量影片本身的质量。符合口味但均分只有 3 分的片子，不应排在前面。

排序阶段引入**物品质量信号**，在召回分之外再评估影片是否值得推荐：

<Math block>{`\\begin{aligned}
\\text{final\\_score} &= 0.5 \\times \\text{recall\\_norm} \\\\
&\\quad + \\; 0.3 \\times \\text{rating\\_norm} \\\\
&\\quad + \\; 0.2 \\times \\text{popularity\\_norm}
\\end{aligned}`}</Math>

精排前后排名变化示例：

| 电影                    | 召回排名 | 精排后 | 原因                             |
| ----------------------- | -------- | ------ | -------------------------------- |
| Raiders of the Lost Ark | 1        | 2      | 召回分最高，但质量信号不如肖申克 |
| Shawshank Redemption    | 2        | 1      | 评分 9.1 + 310 万人评            |
| Godfather: Part II      | 未进前 5 | 5      | 评分 8.7 + 210 万人评，热度补位  |

## 与工业级系统的差距

这是一个完整但精简的实现；与工业级系统的差距主要在规模与精度，架构形态相近：

| 环节 | 本项目                   | 工业级应用               |
| ---- | ------------------------ | ------------------------ |
| 数据 | MovieLens pkl 文件       | 数据仓库 + 实时日志流    |
| 召回 | popular + genre + ItemCF | 同 + 向量召回 + DNN 召回 |
| 排序 | 手写线性公式             | DeepFM / DIN / Wide&Deep |
| 服务 | FastAPI + pandas 内存    | gRPC + Redis + 微服务    |

后续文章将补充向量召回，用 embedding 做语义匹配，扩展召回覆盖面。
