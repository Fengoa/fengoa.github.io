# 从零搭一个推荐系统

你打开 Spotify，首页给你推了一首没听过的歌。你点进去听了，还不错。然后你开始想：它怎么知道我会喜欢这首？

这个问题拆开来其实是两个问题。第一个：Spotify 曲库里有一亿首歌，它凭什么只给你看这 30 首？第二个：这 30 首里，排在第一位的那首凭什么排第一？

第一个问题叫「召回」——从一亿首里快速捞出几百首可能相关的。第二个问题叫「排序」——从几百首里精确挑出最匹配的排在最前面。

一亿首不可能逐个算一遍你喜不喜欢，时间上来不及。所以要先粗筛再细排。粗筛求快，用简单规则大量过滤；细排求准，用更多信号精确打分。

这篇文章记录的就是从零搭一套这样的流水线的过程。数据用的是 MovieLens（电影评分），技术用的是 Python + FastAPI，没有数据库没有 Redis 没有深度学习，但结构和工业界一致。

---

下面是具体怎么搭的。

---

## 核心矛盾

推荐系统要解决的问题：

```text
给用户 u，在所有物品 i 中，找到得分最高的 Top K
score(user, item) → 排序 → Top K
```

矛盾在于：物品太多，不可能给每个物品都算一遍精确得分。4000 部电影还好，4000 万件商品就不行了。

所以工业界把问题拆成两步：

```text
全量物品 → 召回（快速粗筛）→ 排序（精确打分）→ 展示
```

召回负责"找得到"，排序负责"排得准"。

---

## 召回：多种策略打捞候选

召回的目标是从全量物品里快速捞出一批"可能相关"的候选。要快，也要多样。

单一策略有盲区——热门召回不了解个人偏好，协同过滤对冷门长尾无能为力，类型匹配缺少协同信号。所以实际系统都是多路并行：

```text
多路召回（各取 40 部候选）
  ├─ 热门召回        → 评分人数多 + 均分高的电影
  ├─ 类型偏好召回    → 用户常看类型的高分电影
  └─ ItemCF 召回    → 协同过滤相似电影
```

### 热门召回

最朴素的策略：找评分人数多、均分高的电影。不依赖用户历史，是兜底策略——新用户、冷启动都能用。

### 类型偏好召回

统计用户看过的电影类型分布，按出现频率算权重。看了 7 部 Drama、3 部 Comedy，那 Drama 权重 0.7、Comedy 权重 0.3。从对应类型里按权重选高分电影。

直觉：一个人的品味有惯性。

### ItemCF 召回

ItemCF 的直觉：

```text
喜欢 A 的人也喜欢 B → A 和 B 相似 → 用户看过 A，推荐 B
```

具体做法是离线扫一遍所有用户的行为，统计物品之间的共现关系，算出每个物品的相似物品列表。在线时只需要查表：用户喜欢哪些电影 → 这些电影的相似电影有哪些 → 合并打分。

一个细节：活跃用户看过几百部电影，如果不加处理，会让所有物品两两相似。所以要用 IUF（Inverse User Frequency）加权——看得越多的用户，每次共现的贡献越低：

```text
weight = 1 / log(1 + 用户看过的电影数)
```

和搜索引擎里的 IDF 同一个直觉：出现太频繁的信号，信息量低。

离线构建相似表，在线只查表——"离线计算、在线服务"的基本范式。

---

## 合并：归一化是关键

三路召回各自返回候选和分数，但分数尺度完全不同：

```text
热门召回：recall_score = 评分人数（几十到几千）
类型召回：recall_score = 类型权重 × 均分（0 到 10）
ItemCF：  recall_score = 相似度累加（0 到 几）
```

直接加起来没有意义。先归一化到 [0, 1]：

```text
normalized = (score - min) / (max - min)
```

归一化之后按权重合并：

```text
merged_score = 0.5 × itemcf_norm + 0.3 × genre_norm + 0.2 × popular_norm
```

权重反映对每路召回的信任程度。ItemCF 最个性化，权重最高；热门最泛化，权重最低。

合并之后去掉用户已看过的电影，输出候选集。

---

## 排序：加入物品质量信号

召回阶段只关心"这部电影和用户有没有关系"，没考虑电影本身好不好。一部和用户口味匹配但只有 3 分的烂片，不应该排在前面。

排序阶段引入物品质量信号：

```text
final_score = 0.5 × recall_score_norm    （召回置信度）
            + 0.3 × avg_rating_norm      （用户评分质量）
            + 0.2 × popularity_norm      （多少人看过）
```

三个信号各自归一化后加权。效果：

| 电影 | 召回排名 | 精排后 | 原因 |
|------|---------|--------|------|
| Raiders of the Lost Ark | 1 | 2 | 召回分最高，但质量信号不如肖申克 |
| Shawshank Redemption | 2 | 1 | 评分 9.1 + 310 万人评，质量拉满 |
| Godfather: Part II | 未进前 5 | 5 | 评分 8.7 + 210 万人评，热度补位 |

召回决定"能不能被看到"，排序决定"排第几"。

## 代码结构

```text
recommender/
  loader.py       # 数据加载，统一 ID 类型
  recall.py       # 三路召回 + 归一化合并
  ranker.py       # 精排打分
main.py           # FastAPI，对外暴露 /recommendations
scripts/
  build_itemcf.py # 离线构建 ItemCF 相似表
```

最终接口：

```text
GET /recommendations?user_id=1&top_k=20

→ 内部流程：
  popular_recall(40) ─┐
  genre_recall(40)   ─┼→ 归一化合并(50) → rank_candidates → Top 20
  itemcf_recall(40)  ─┘
```

## 和工业界的距离

| 环节 | 这个项目 | 工业界 |
|------|---------|--------|
| 数据 | MovieLens pkl 文件 | 数据仓库 + 实时日志流 |
| 召回 | popular + genre + ItemCF | 同 + 向量召回 + DNN 召回 |
| 合并 | 归一化加权 | 同，可能加去重/打散策略 |
| 排序 | 手写线性公式 | DeepFM / DIN / Wide&Deep |
| 服务 | FastAPI + pandas 内存 | gRPC + Redis + 微服务 |
| 存储 | 本地文件 | PostgreSQL / HBase / S3 |

区别在规模和精度，结构上是一回事。手写公式和 DeepFM 做的是同一件事——给 `score(user, item)` 建模。一个用三项加权和，一个用几百万参数的神经网络。
