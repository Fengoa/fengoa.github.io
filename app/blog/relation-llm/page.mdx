# 非结构化关系记忆：口语笔记到可查询图谱

客户关系中真正有业务价值的信息，经常散落在即时通讯草稿、随手笔记和口头交代里：「老高的生日是农历六月初八」「小张是老高介绍来的客户」「王姐昨天到店做了美甲，消费一百二十八元」。

传统 CRM 能存结构化字段，但要求人先填表；全文检索能搜到原文，却很难稳定回答「未来三十天谁过生日」「老高通过中间人还能联系到哪些人」「谁和老高关注同一类市场」。

进一步的问题是：能否做成这样一种产品——用户输入保持口语习惯，系统负责抽成可查询的记忆：精确查属性、沿关系展开、按语义找相近的人与事。

## 要解决什么问题

一段无固定格式的中文口语文本进来之后，系统至少要产出三样东西：实体、关于实体的事实、实体之间的关系边。在此之上，常见查询有四类：

- **属性精确查询**：某人当前生日、过敏、头衔是什么；
- **时间窗口查询**：未来 <Math>{`d`}</Math> 天内谁过生日；
- **关系邻域查询**：从某人出发，沿介绍/同事等边向外走最多 <Math>{`k`}</Math> 层，能到达谁；
- **语义近邻查询**：自然语言问句与哪段笔记、哪个实体画像相近。

全文检索难以完成历法换算与关系链展开；表单 CRM 字段完整，却把结构化成本转嫁给录入者。设计前提是：**录入保持口语，结构化交给系统**。

一段正向示例输入：

> 老高的生日是农历六月初八。小张是老高介绍来的客户。王姐昨天到店做了美甲，消费一百二十八元。老高最近在关注新能源出海拉美市场。

期望至少得到：老高的生日状态、老高介绍小张的边、王姐一笔 128 元消费事件、老高的兴趣状态；并据此回答生日窗口、一层/两层关系邻域，以及与「拉美电动车市场」语义相近的兴趣记录。

## 记忆有三种形状

落库前先分清数据形态。形态不同，写入语义就不同；若强行并入同一张宽表，覆盖策略与查询语义会相互冲突。

**状态型事实（state）**：实体某一属性上的当前状态——头衔、生日、过敏、称呼偏好、预算意向。同一实体、同一属性，同一时刻只应有一条有效记录。新值写入时，旧值写上 `valid_to`，历史可追溯，当前值不混淆。

**事件型记录（event）**：不可覆盖的流水——消费、库存变动、会面。每次发生新增一行，带 `event_time` 和可选的 `value_amount`，方便区间过滤和求和。

**关系型连接（relationship）**：实体之间的有向边——介绍、同事、合作伙伴、上下级。邻域查询和路径展开需要边作为一级结构，不宜放入事实表的某个 JSON 字段。

| 类型 | 典型属性 / 标签 | 写入语义 |
|------|-----------------|----------|
| state | birthday、allergy、title、preference | 覆盖：关闭旧 `valid_to`，插入新行 |
| event | transaction、inventory_change、meeting | 仅追加 |
| relationship | introduced_by、colleague、partner | 写入边表 |

「郑总升职为华东区总经理」是状态覆盖；「王姐消费一百二十八元」是事件流水；「小张是老高介绍来的」是关系边。抽取阶段必须先**三分类**，再按各自规则写入。

## 存储：用 PostgreSQL 同时覆盖三类需求

结构化过滤、JSONB 灵活字段、向量近邻，可以先放在同一个 PostgreSQL 实例里：关系表与索引负责精确路径，`JSONB` 负责开放属性值，向量扩展负责语义检索。独立图库或独立向量库，等到关系展开变成高频主路径、或事实规模明显变大时再评估。

### 核心表

**entities**：规范名 `canonical_name`、类型 `entity_type`、别名数组 `aliases`。

**facts**：外键 `entity_id`；`fact_type` 取 `state_fact` 或 `event`；开放字符串 `attribute`；`value JSONB`；派生列 `value_normalized_date`、`value_amount`；`event_time`；原文 `raw_text`；向量 `embedding`；`confidence`；`is_sensitive`；`source`；有效期 `valid_from` / `valid_to`。

**relationships**：`entity_a_id`、`entity_b_id`、`relation_type`，以及可选的 `sentiment` / `note`、`raw_text`、`confidence`。

**entity_embeddings**：每个实体一条聚合向量，供「关联发现」做实体级近邻。

索引方面：`(entity_id, attribute, fact_type)` 支持精确属性查询；`value` 上的 GIN 支持 JSON 内检索；`value_normalized_date` 部分索引支持可索引日期过滤；关系表两端各建索引。向量侧在小规模（数千条以内）可以直接顺序扫描——样本极少时，部分近似索引若探测参数过小，反而会漏掉本应命中的行。

### 派生列与开放 value

全部过滤都解析 JSONB，范围查询和聚合又慢又难走索引。于是从 `value` 里抽出两类高频标量：`value_normalized_date`（可静态索引的日期）、`value_amount`（金额或数量）。属性名保持开放，热路径仍然可索引。

日期类事实用统一结构表达历法与月日，例如：

```json
{"primary": {"calendar": "lunar", "month": 6, "day": 8, "leap": false}}
```

周期性日期（尤其农历）有一个实现要点：**不宜在写入时换成某一年的公历后永久固化**，因为每年对应的公历日不同，且存在闰月。库中保留历法字段，时间窗口查询时再换算「下一个出现日」。信息不完整时用 `known: false` 显式标记，提醒类查询直接跳过，避免臆造日期。

## 写入：两遍抽取

入口接收文本字段 `text` 和可选来源 `source`。拆成两遍，是因为**事实抽取**和**关系指代消解**的约束不一样。

### 第一遍：实体与事实

大模型按结构化 JSON 返回，例如：

```json
{
  "records": [
    {
      "type": "state_fact",
      "entity": {"name": "老高", "entity_type": "person"},
      "attribute": "birthday",
      "value": {"primary": {"calendar": "lunar", "month": 6, "day": 8, "leap": false}},
      "raw_text": "老高的生日是农历六月初八。",
      "confidence": 0.95
    }
  ]
}
```

提示词中的强制约束：

1. **先三分类，再填字段**；
2. `attribute` 开放，给常见例子但不穷举；
3. 每条必须带 `confidence` 和 `raw_text`；
4. 普通文本值必须是对象（如 `{"text":"交互式设计师"}`），日期走统一结构；
5. 一句多属性拆成多条（「公历生日七月二十日，不喜欢别人送花」→ birthday + gift_preference）；
6. 「端午节员工礼盒」里的节日名是商品名一部分，不得解析成日期。

第一遍产出的 `relationship` 可以先不写库，交给第二遍拿完整实体名单再抽，指代更稳。

### 第二遍：关系与指代消解

事实入库后，读出当前全部实体规范名，构成名单。第二遍只输出两端都在名单里的关系边，并把「我们组」「组员」「他」「几个人」映射到具体名字。

开放世界的命名问题，由此收束为**闭集指代**：边的端点不能发明名单外的新名字。新实体应在第一遍以事实主体出现并入库，再进入第二遍名单。

### 置信度闸门

`confidence < 0.6` 的记录不自动入库，放入 `needs_confirm` 交给确认界面。阈值可调：过低会漏记，过高会把噪声写入图谱。确认 / 修改 / 驳回的路径必须短于重新手写笔记，否则使用者会弃用系统。

## 归一化与实体解析

### 实体解析顺序

落库时对名字按这个顺序解析：

1. 规范名精确匹配（大小写不敏感）；
2. 别名数组精确命中；
3. 昵称核心模糊匹配：去掉「老 / 小 / 大 / 阿」前缀和「哥 / 姐 / 总」等后缀后做子串匹配；**只有唯一命中才合并**，并把原昵称写入 `aliases`；
4. 否则新建实体。

「唯一命中才合并」采取保守策略：误把两个人并成一个，比多建一个实体更难修复。

### 去重与状态覆盖

插入前检查同一实体、同一属性、同一 `raw_text` 是否已存在；相同原文的重试直接跳过，避免超时重放产生重复行。

状态型事实先关闭旧值：

```sql
UPDATE facts
SET valid_to = now()
WHERE entity_id = $1
  AND attribute = $2
  AND fact_type = 'state_fact'
  AND valid_to IS NULL;
```

再插入新行。查「当前值」时过滤 `valid_to IS NULL`。

### 向量：事实级与实体级

每条入库事实对 `raw_text` 做嵌入，写入 `facts.embedding`。同时把该实体下所有事实向量做分量平均，写入 `entity_embeddings`：

<Math block>{`
\\mathbf{v}_e = \\frac{1}{|F_e|} \\sum_{f \\in F_e} \\mathbf{v}_f
`}</Math>

实体级向量用于「谁和某人整体画像相近」；事实级向量用于「哪段笔记和问句相近」。二者粒度不同，应分开使用。

## 召回：三条主路径

### 实体时间线

按规范名或别名找到实体，返回事实列表，排序键 `COALESCE(event_time, valid_from) DESC`。对外就是一份档案时间线：状态变更和事件流水交织，原文可追溯。

### 关系邻域：递归 CTE

从中心实体沿有向边展开，深度上限常取 4（并设置绝对上限），用路径数组防环：

```sql
WITH RECURSIVE network AS (
  SELECT entity_a_id, entity_b_id, relation_type, 1 AS depth,
         ARRAY[entity_a_id, entity_b_id] AS path
  FROM relationships
  WHERE entity_a_id = (
    SELECT id FROM entities WHERE canonical_name = '老高' LIMIT 1
  )
  UNION ALL
  SELECT r.entity_a_id, r.entity_b_id, r.relation_type, n.depth + 1,
         n.path || r.entity_b_id
  FROM relationships r
  JOIN network n ON r.entity_a_id = n.entity_b_id
  WHERE n.depth < 4
    AND NOT r.entity_b_id = ANY(n.path)
)
SELECT * FROM network ORDER BY depth;
```

**一层关系**：直接相连（老高介绍小张）。**两层关系**：中间隔一个人（老高 → 小张 → 李总）。「通过中间人还能联系到谁」，对应的就是深度为 2 的邻域。

若写入时边方向不统一（「A 介绍了 B」与「B 是 A 介绍来的」），查询要考虑双向，或在写入时统一方向。可以先沿 `entity_a → entity_b` 单向展开，再按数据表现决定是否 `UNION` 反向。

### 语义检索

问句先嵌入，再在事实表上按距离排序。用余弦距离算子时，相似度可以写成：

<Math block>{`
\\mathrm{sim}(q,f) = 1 - \\bigl(\\mathbf{v}_q \\Leftrightarrow \\mathbf{v}_f\\bigr)
`}</Math>

其中 <Math>{`\\Leftrightarrow`}</Math> 表示向量扩展里的余弦距离。可选按 `attribute` 过滤（例如只搜 `interest`）。这条路径覆盖「关键词不重叠、语义仍相关」的撮合，例如「关注新能源出海拉美」和「想认识电动汽车拉美市场的朋友」。

### 时间窗口与查询路由

生日提醒属于时间窗口查询：取出当前有效的 birthday 状态事实，按前述「查询时换算」得到下一个出现日，再与窗口求交。实体名、属性词明确时，优先走结构化查询；问句含糊时，优先走向量。也可以两条并行再取并集。关键是**结构化、关系邻域、向量三条路径互补**。

## 关联发现：不预置规则边

显式关系边之外，查询时还可推导两类「软关联」，并且不写回 `relationships`，避免边爆炸：

1. **语义邻近**：用中心实体的聚合向量做近邻，得到画像相近的人（同好、同行、相近背景）；
2. **共享属性桥接**：找出与中心实体有相同 attribute + value 的其他实体，关联标签就是该属性值本身（如同过敏原、同偏好）。

前者依赖 `entity_embeddings`；还没生成时，语义邻近为空。后者是集合交，可解释性更好。

## 接口一览

| 能力 | 方法与路径 | 输入要点 | 输出要点 |
|------|------------|----------|----------|
| 入库 | `POST /api/ingest` | `text`，可选 `source` | `extracted` / `stored` / `relationships` / `needs_confirm` / `errors` |
| 时间线 | `GET /api/entities/:name` | 实体名 | 实体元数据 + 事实列表 |
| 关系邻域 | `GET /api/network` | `entity`，可选 `depth` | 有序边列表（含深度） |
| 语义检索 | `GET /api/search` | `q`，可选 `attribute`、`limit` | 事实 + 相似度 |
| 时间窗口 | `GET /api/upcoming` | 可选 `days` | 窗口内到期的周期性事实 |
| 关联发现 | `GET /api/discover` | `entity`，可选 `limit` | 语义邻近 + 共享属性 |

## 怎么验这些细节

| 场景 | 输入要点 | 验证点 |
|------|----------|--------|
| 三分类与拆分 | 一句含状态 + 关系 + 事件 | 拆成多条，类型正确 |
| 状态覆盖 | 头衔变更两次 | 仅最新行 `valid_to IS NULL`；旧行可追溯 |
| 事件流水 | 多笔消费 | 行数等于次数；金额可聚合 |
| 关系展开 | 介绍链 A→B→C | 深度 1 与深度 2 符合真实连通 |
| 语义撮合 | 兴趣描述无关键词重叠 | 近邻进入结果集 |
| 置信度闸门 | 含糊不清的句子 | 低置信进入 `needs_confirm`，不进入主库 |
| 实体解析 | 「超哥」与「刘超」 | 唯一命中合并并写 alias；多候选不误并 |
| 周期性日期 | 农历生日 + 提醒窗口 | 查询时换算；`known:false` 不进提醒 |

## 边界与后续

当前已具备：三类形态、两遍抽取、状态覆盖与事件追加、关系递归展开、事实级与实体级向量、置信度闸门、共享属性与语义邻近，以及对周期性日期的查询时换算。

仍要注意：

- 关系若只单向展开，可能漏掉方向相反的写入；
- 嵌入维度须与模型一致，换模型要同步改向量列；
- 昵称出现多个候选时暂不合并，可能造成同一人对应多个实体，需要人工合并工具；
- `is_sensitive` 只是标记，「谁能看过敏史 / 财务」属于权限规则，要单独设计；
- 极小规模顺序扫描更稳，大规模再上 HNSW 一类索引并校准召回。

后续可以补：写入时统一边方向、查询双向 `UNION`、轻量路由自动选路径、确认卡片的批量导入与纠错成本度量、多组织隔离键与角色可见性。

## 收束

非结构化关系记忆的关键，在于承认记忆有**状态、事件、关系**三种形状，并在抽取、归一化、落库和召回里贯彻这一区分；额外多调用一次大模型并不能替代这一层结构。口语负责降低录入成本；结构化查询、关系邻域与向量近邻负责把记忆变成可查询资产。形状判断正确时，路径展开、语义撮合以及周期性日期换算才有落点；形状判断错误时，后续能力再强，也只能作用在错误结构上。
