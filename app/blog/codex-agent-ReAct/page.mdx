# Codex Agent 设计原理

<SeriesNav series="agent" />

写完 Codex Agent 的实现之后，回头想真正卡住人的往往不是某段 TypeScript，而是**为什么要这么设计**。这篇不谈代码，只谈原理：ReAct 为什么比单次推理更适合执行型任务、工具 `description` 到底是写给谁看的、截图为什么是铁律而不是建议。代码与伪实现见 [技术实现详解](/blog/codex-agent)。

## 从单次推理到循环推理

### 1.1 旧范式的局限

在 Agent 出现之前，LLM 的工作方式是**单次推理**：给定一个问题，LLM 在一次调用中生成完整答案。这个范式对于"知识型"任务表现良好——解释一个概念、翻译一段文字、撰写一篇文章——因为这类任务所需的一切信息都存在于模型的权重中，不需要与外部世界交互。

但当任务变为"执行型"时，单次推理就力不从心了：

- "帮我登录这个网站并下载报表"——LLM 不知道登录后的页面长什么样
- "帮我处理这个 CSV 文件"——LLM 不知道文件里有什么数据
- "帮我找到所有 404 错误并修复"——LLM 不知道执行命令后的实际输出

单次推理的根本问题是：**它假设推理所需的全部信息在推理之前就已存在**。但现实世界的任务往往是"边走边看"的——你必须先做一步，才能知道下一步该怎么做。

### 1.2 ReAct 的核心洞见

ReAct（Reasoning + Acting）范式的核心洞见只有一句话：

> **把一个大任务，拆解为无数个"小决策 → 小行动 → 小观测"的循环。**

每一轮循环的规模极小，小到 LLM 只需要根据当前已知信息做出一个局部最优的决策即可。错了没关系，因为下一轮循环会观测到错误并有机会纠正。

这与人类处理复杂任务的方式完全一致。当你学习一项新技能时，你不会在开始前就规划好每一个动作。你做一个动作，观察结果，感受反馈，调整，再做下一个动作。Agent 的工作方式与此同构。

### 1.3 Loop 的终止：Agent 何时认为任务完成

这是一个微妙但重要的问题。Agent Loop 的终止条件不是"达到了某个预定义的状态"，而是"LLM 判断任务已完成、不再需要调用工具"。

这意味着终止逻辑完全依赖 LLM 的判断，而 LLM 的判断依赖于它在最后一轮能"看到"足够的证据。对浏览器 Agent 来说，这个证据通常是截图——截图中显示了任务成功的视觉证据（如"下载完成"的提示、数据已出现在列表中等）。

**实践含义**：在系统提示中明确告诉 Agent"任务完成的标志是什么"，能显著提高终止判断的准确性。

### 1.4 与 Chain-of-Thought 的根本区别

Chain-of-Thought 让 LLM "在脑中演算"，所有推理在一次调用中完成，不与外部世界交互。ReAct 让 LLM "在世界中演算"，每一步推理都可能改变外部状态，而改变的结果又成为下一步推理的依据。

|                  | Chain-of-Thought     | ReAct / Agent Loop         |
| ---------------- | -------------------- | -------------------------- |
| 与外部世界的关系 | 无（完全在模型内部） | 持续交互                   |
| 错误恢复         | 不支持（错了就错了） | 支持（观测到错误后可纠正） |
| 任务类型         | 信息已知、答案封闭   | 信息待发现、答案开放       |
| 推理轮数         | 一次                 | 多次，直到收敛             |
| 类比             | 闭卷考试             | 做实验                     |

## 工具：AI 与真实世界的接口合约

### 2.1 工具的本质是"能力的边界声明"

当我们为 LLM 定义一个工具时，我们实际上在做两件事：

第一，**告诉 LLM 它能做什么**。工具的 `description` 字段是 LLM 决定"是否使用这个工具"的主要依据。描述写得清晰，LLM 就能在正确的场景选择正确的工具；描述含糊，LLM 就会频繁误用。

第二，**约定 AI 与执行环境的数据格式**。工具的 `input_schema` 是一份合约——LLM 承诺按照这个 Schema 生成参数，执行层承诺按照这个 Schema 解析参数。这个合约的清晰程度直接决定了系统的健壮性。

**一个常见误区**：认为工具描述是给人看的文档。错。工具描述是给 LLM 读的指令。它需要回答的核心问题不是"这个工具做什么"，而是"在什么情况下应该用这个工具，而不是其他工具"。

### 2.2 工具粒度的设计哲学

工具粒度是 Agent 设计中最难拿捏的问题之一。

**粒度过粗**：一个"操作浏览器"工具，什么都能做。LLM 必须学会用自然语言描述具体操作，执行层必须解析这些描述。这引入了大量的歧义空间，很难稳定运行。

**粒度过细**：`browser_click_by_css`、`browser_click_by_text`、`browser_click_by_coordinate` 三个分开的工具。LLM 必须在调用前就决定用哪种定位方式，但很多时候在截图之前它不知道哪种方式最合适。

**Codex 的答案**：以"用户意图"为粒度，而不是以"技术实现"为粒度。`browser_click` 工具支持多种定位方式（CSS、文字、坐标），由执行层按优先级尝试。LLM 只需要表达"点击这个元素"的意图，不需要关心如何定位。

这个设计原则可以推广：**工具的边界应该对应 LLM 的一个"意图单元"，而不是一个"技术动作单元"**。

### 2.3 为什么工具结果必须"对 LLM 友好"

工具的执行结果（Observation）会被注入到下一轮的上下文中，供 LLM 推理。如果结果格式对 LLM 不友好，推理质量就会下降。

几个关键原则：

**错误信息必须具体**。"操作失败"对 LLM 毫无帮助；"元素 #submit-btn 未找到，当前页面 URL 为 /login，可能需要先完成登录"则能让 LLM 立刻调整策略。

**成功结果要包含状态摘要**。"点击成功"过于简短；"已点击'提交'按钮，当前 URL 未变化，建议截图确认提交结果"给了 LLM 足够的上下文决定下一步。

**数据量要适中**。返回一个 10 万行的 CSV 给 LLM 没有意义；返回"已提取 1,240 行数据，前 5 行为：[...]，已保存到 /workspace/data.csv"才有用。**Observation 的职责是让 LLM 知道发生了什么，而不是把所有数据都塞给它**。

## 上下文：Agent 的唯一工作记忆

### 3.1 LLM 没有记忆，只有上下文

这是理解 Agent 设计的最基础的认知：LLM 是无状态的。每次调用都是全新的，它不记得上一次调用说了什么。Agent 的"记忆"完全由程序层维护——即对话历史（Message History）。每次调用 LLM 时，都要把所有历史一起发送过去。

这意味着上下文窗口是 Agent 的"工作记忆容量上限"。当任务足够复杂、历史足够长时，旧的信息会被挤出窗口，Agent 就会"遗忘"。

### 3.2 上下文的四类内容及其优先级

一个 Agent 的上下文通常包含以下内容，优先级从高到低：

**系统提示（System Prompt）**：定义 Agent 的行为准则、工具使用规范、任务目标格式。这是 Agent 的"操作系统"，必须始终占据上下文的首位，且内容需要精简——每一个字都会消耗宝贵的 token 配额。

**环境信息（Environment Info）**：当前时间、工作目录、浏览器状态、已完成步骤数等动态信息。这些信息让 LLM 对"它现在在哪里"有清晰的认知，是防止 LLM"迷失"的关键。

**工具 Schema**：LLM 需要在每次调用时都能看到完整的工具列表，才能决定用哪个工具。这部分内容相对稳定，但占据不小的 token 空间。

**对话历史（Message History）**：所有过去的 user/assistant/tool 消息。这是最"贵"的部分，也是最容易撑爆上下文的部分。

### 3.3 历史管理的三种策略

随着任务延长，历史管理是不可回避的工程问题。三种主流策略各有适用场景：

**硬截断（Sliding Window）**：只保留最近 N 条消息。实现简单，但如果任务的关键上下文在早期消息中，截断后 Agent 会"失忆"。适合任务相对简单、步骤之间依赖性弱的场景。

**摘要压缩（Summarization）**：用一个轻量 LLM 将旧消息压缩为摘要，摘要替换原始消息。能保留更多信息，但摘要质量依赖压缩模型，且摘要本身不可撤销——一旦压缩，原始信息永久丢失。

**检查点（Checkpointing）**：定期保存关键状态（已提取的数据、已完成的步骤、当前目标进度），而不是保存完整的对话历史。后续轮次只需要从检查点恢复状态，不需要重放所有历史步骤。这是最高效的策略，但需要预先设计好"状态"的数据结构。

**实践建议**：对于浏览器自动化任务，截图占用大量 token。策略应该是"最近 2-3 张截图 + 早期截图的文字摘要"，而不是保留所有截图。

### 3.4 系统提示的设计原则

系统提示不只是"告诉 LLM 它是谁"的地方，更是**行为规范的定义层**。对浏览器 Agent 来说，以下几类内容必须在系统提示中明确：

**操作顺序约束**：截图 → 操作 → 截图确认。不能跳过"截图确认"这一步，因为没有视觉反馈，LLM 无法判断操作是否成功。

**错误处理协议**：遇到什么情况需要重试？重试几次后需要改变策略？什么情况下应该放弃并报告失败？

**数据流转规则**：浏览器提取的数据如何传递给 CLI 工具？中间文件放在哪里？格式是什么？

**任务完成的判断标准**：什么视觉状态或数据状态代表任务成功完成？这是终止条件的核心。

## 观测：Agent 的感知哲学

### 4.1 Observation 是"世界状态的编码"

Agent 无法直接感知世界——它不能"看"网页，不能"摸"文件，不能"听"命令执行。它能做的只有一件事：**读取上下文中的文字和图像**。

Observation 的职责就是把真实世界的状态，翻译成 LLM 能读懂的形式。这个翻译过程的质量，决定了 Agent 推理的质量上限。

真实世界的状态可以用三种形式编码：

**视觉编码（截图）**：把页面当前状态拍下来，以图像形式传给 LLM。这是最完整的编码，因为它保留了所有视觉信息——布局、颜色、文字位置、表单状态。代价是 token 消耗大。

**结构编码（DOM/JSON）**：提取页面的结构化数据——元素的选择器、文字内容、属性值、表格数据。这是最精确的编码，适合需要精确数据的场景。代价是丢失了视觉上下文，LLM 可能难以理解元素的相对关系。

**文本编码（stdout/logs）**：命令执行的文字输出。最轻量，但只适合文字化的信息。

**关键洞见**：三种编码不是互斥的，而是互补的。对于浏览器操作，截图用于"确认状态和定位元素"，DOM 提取用于"获取精确数据"。通常先截图判断页面状态，再用 DOM 提取获取具体数值。

### 4.2 为什么"先截图，后操作"是铁律

在浏览器 Agent 中，"截图优先"不是建议，而是铁律。原因有三：

第一，**页面状态不可预测**。网页可能有 loading 动画、弹窗、重定向、动态内容加载。如果不截图直接操作，LLM 是在"盲操"——它假设页面处于某个状态，但实际上可能完全不同。

第二，**定位元素需要视觉上下文**。"点击提交按钮"这个指令要落地，需要知道提交按钮在哪里。CSS 选择器有时会失效（动态 class、多个匹配元素），而截图能让 LLM 通过坐标直接定位，更加稳健。

第三，**操作结果需要视觉确认**。LLM 无法通过 DOM 变化判断"表单是否真的提交成功了"，但截图中的"提交成功"消息、页面跳转、确认弹窗是无可争议的证据。

### 4.3 Observation 的"信息密度"原则

并非所有 Observation 的内容都同等重要。好的 Observation 设计遵循"**高信息密度、低冗余**"原则：

告诉 LLM"发生了什么"（状态变化），而不是"有哪些数据"（原始数据）。例如：

- 不好：返回完整 HTML（几万字符，绝大部分 LLM 用不上）
- 更好：返回「页面已加载，标题为『用户管理』，检测到数据表格，共 47 行」

告诉 LLM"有什么异常"，而不是"一切正常"。成功的操作可以用一句话描述，失败的操作需要提供足够的诊断信息。

## Approval：渐进式信任模型

### 5.1 信任不是二元的

很多人把 Approval 系统理解为"是否信任 AI"的问题，这是错误的框架。正确的框架是：**不同的操作类型，需要不同程度的信任，而信任是可以随着使用逐步建立的**。

以人类工作协作为类比：你刚雇了一个助手，第一天你会审查他写的每封邮件；一个月后，你信任他能独立处理普通邮件，但财务审批还需要你点头；半年后，一些小额财务也可以授权给他。Codex 的三层 Approval 模式本质上是在模拟这个过程。

### 5.2 三层 Approval 模式的设计逻辑

**Suggest（建议模式）**：Agent 只产生建议，不执行任何操作。所有工具调用都以"建议"形式呈现给用户，用户决定是否执行。这是信任最低的模式，适合初次使用或高风险场景。代价是效率极低，需要用户大量参与。

**Auto-edit（选择性自动执行）**：低风险操作（读文件、截图、提取数据）自动执行；高风险操作（执行 shell 命令、写文件、导航到外部 URL）需要用户确认。这是大多数生产场景的推荐模式。

**Full-auto（全自动沙箱模式）**：所有操作都在隔离的沙箱环境中自动执行，沙箱限制了 Agent 能访问的资源范围（文件系统、网络、进程权限）。信任不是给 Agent 的，而是给沙箱边界的。这是自动化流水线的推荐模式。

### 5.3 沙箱的本质：把信任转移给边界

Full-auto 模式的关键洞见是：**不需要信任 Agent 的每个决策，只需要信任沙箱的边界足够安全**。

沙箱边界通常包含：

- **文件系统隔离**：Agent 只能读写指定的工作目录，不能访问系统文件或用户数据
- **网络隔离**：Agent 只能访问白名单中的域名，防止数据外泄和 SSRF 攻击
- **进程权限限制**：不能以 root 权限执行、不能 kill 其他进程、不能修改系统配置
- **资源限制**：CPU、内存、磁盘 I/O 上限，防止 Agent 的一次错误操作耗尽系统资源

**对浏览器平台的含义**：浏览器本身就是天然的沙箱——它的同源策略、权限模型、进程隔离已经提供了相当强的安全边界。在此基础上，只需要额外控制"Agent 能够导航到的域名白名单"和"能够下载/执行的文件类型"，即可构建足够安全的 Full-auto 模式。

## 流式输出

### 6.1 为什么流式输出不只是"更好的用户体验"

流式输出（Streaming）常被视为一个 UX 改进——让用户看到"正在思考"的过程，而不是等待一个空白后突然出现完整结果。但对 Agent 来说，Streaming 还有更深的架构意义。

LLM 的输出是顺序生成的：先生成推理文字，再生成工具调用参数。在流式模式下，执行层可以在工具调用参数**还没生成完**时就开始准备（如初始化浏览器连接、预热执行环境），从而减少端到端延迟。

更重要的是，流式输出允许执行层**在中途检测到工具调用的意图**，提前向用户展示"Agent 即将执行什么操作"，再一次提供了插入人工干预的机会。

### 6.2 Streaming 与 Tool Call 检测的时序问题

这是 Streaming 实现中最微妙的问题：工具调用的参数是以 JSON 片段形式流式生成的（`partial_json_delta`），执行层需要把这些片段拼接成完整 JSON 后才能解析参数。

这意味着：LLM 开始生成工具调用后，执行层需要一直缓冲，直到这个工具调用块完全结束，才能真正执行。但与此同时，文字推理内容可以实时渲染给用户，让用户看到 Agent 的"思考过程"。

时序上，一个典型的流式响应看起来像：

```
[文字开始流出] "我需要先截图查看当前页面状态..."
[检测到 tool_call 开始] → UI 显示"正在截图..."
[tool_call 参数流式积累中，JSON 尚不完整]
[tool_call 参数积累完毕] → 真正执行截图
[返回截图结果] → 进入下一轮
```

## 视觉接地

### 7.1 DOM 的陷阱：结构与视觉的分离

初学者设计浏览器 Agent 时，往往优先考虑 DOM 操作：提取元素、通过选择器点击、读取属性值。这看起来很"精确"，但存在一个根本性的问题：**DOM 结构和视觉呈现是两个不同的世界**。

同一个 DOM 元素，在不同的 CSS 状态下，视觉上可能完全不同（disabled、hidden、covered by overlay）。一个按钮在 DOM 中存在，但视觉上被弹窗遮挡——CSS 选择器能找到它，但点击会失败或点到错误位置。

更根本的问题是：网页是为**人眼**设计的，不是为 DOM 解析器设计的。一个表格的语义结构（"这一列是价格，那一列是日期"）体现在视觉排列中，而不一定体现在 DOM 的 class 或 id 中。

### 7.2 视觉接地的三个层次

视觉接地（Visual Grounding）是指 Agent 把视觉信息（截图）与操作意图（点击、提取）关联起来的能力。它有三个递进的层次：

**第一层：状态确认**。截图用于确认"当前页面是什么状态"——是否加载完成、是否有弹窗、是否跳转到正确页面。这是最基础的视觉用途，每次导航和操作后都需要。

**第二层：元素定位**。LLM 通过分析截图，识别出目标元素的视觉位置（如"提交按钮在截图中大约在中间偏右，坐标约 (720, 480)"），然后用坐标点击。当 CSS 选择器不可靠时，这是最稳健的定位方式。

**第三层：内容理解**。LLM 通过分析截图理解页面的语义——"这是一个分页列表，当前在第 3 页，共 12 页"、"这个表格的列标题是产品名称、单价、库存量"。这种理解超越了 DOM 能提供的信息，是视觉接地最强大的能力。

### 7.3 截图的最优使用策略

截图消耗大量 token（一张 1280×800 的截图在高质量模式下约消耗 1,500+ token），不能无节制地截。最优策略是：

**定点截图**（常规操作）：每次"导航"或"重要点击"后截一次，用于确认操作结果。这是基线。

**局部截图**（精准定位）：当需要定位某个特定区域的元素时，只截该区域的图。例如，要填写一个表单，只截包含表单的区域，而不是整个页面。

**全页截图**（数据探索）：当需要了解页面的全貌（如爬取一个陌生页面的结构）时，一次全页截图比多次局部截图更高效。

**不截图的场景**：纯 CLI 操作（命令执行、文件处理）不需要截图，命令的 stdout 就是完整的 Observation。浏览器的"等待"操作（等待加载、等待元素出现）也不需要截图，成功/失败的文字信息足够。

### 8.1 为什么 Browser 和 CLI 不能各自为战

浏览器工具和 CLI 工具是两个独立的执行环境，彼此不知道对方做了什么。如果没有共享状态，它们之间的协作只能通过 LLM 的上下文来隐式传递——LLM 把浏览器提取的数据转述给 CLI 工具，CLI 工具的结果再转述给浏览器。

这种"LLM 作为中间人"的传递方式有明显缺陷：

- 数据经过 LLM 转述，可能丢失精度（浮点数、特殊字符、大量数据）
- 大量数据无法通过上下文传递（token 限制）
- LLM 可能在转述过程中引入错误（幻觉）

解决方案是建立一个**程序层的共享状态**（Shared State），让两类工具都能读写同一份数据。LLM 只需要知道"数据已经保存到共享状态的哪个键"，不需要直接传递数据内容。

### 8.2 共享状态的设计原则

共享状态不是全局变量，它需要遵循几个设计原则才能在复杂任务中保持可靠：

**单一数据源**：每份数据只在一个地方存储。浏览器提取的表格数据存在 `shared.extractedData.salesTable`，CLI 处理后的结果存在 `shared.processedResults.salesAggregation`。这两者明确区分，不混用。

**写入即验证**：工具向共享状态写入数据时，应该立刻验证数据格式和完整性。发现格式错误比等到后续工具使用时出错要好得多。

**检查点机制**：在关键步骤（如完成一个阶段性目标）后，把共享状态快照存入检查点。如果后续步骤失败，可以回滚到检查点，而不是从头开始。

**可观测性**：共享状态的当前内容应该以摘要形式注入到 LLM 的系统提示中（如"已提取数据：sales_table(247行)，processed_results：待处理"）。这让 LLM 随时知道任务的整体进度，避免重复执行已完成的步骤。

### 8.3 数据在 Browser 和 CLI 之间的流转模式

实践中，Browser 提取的数据传递给 CLI 有两种主流模式：

**文件中转模式**：Browser 提取数据 → 写入临时 JSON/CSV 文件 → CLI 工具读取文件处理 → 写入结果文件 → Browser（若需要）读取或展示结果。这是最简单可靠的模式，文件路径是唯一需要传递的信息。

**内存中转模式**：Browser 提取数据 → 存入共享状态 → LLM 在下一次 CLI 工具调用时，把共享状态中的数据以 stdin 形式传入。适合数据量较小的场景，避免了文件 I/O，但有 token 传输和命令行长度的限制。

**推荐原则**：数据量 < 10KB，用内存模式；数据量 >= 10KB，用文件模式。

## 任务分解

### 9.1 三个抽象层次

一个典型的浏览器自动化任务，在 Agent 架构中会经历三个抽象层次的映射：

**用户目标层**（自然语言）
"登录网站，下载上个月的销售报表，计算各产品线的总收入"

↓ 任务规划器分解

**步骤层**（有序任务队列）

1. 导航到登录页
2. 填写账号密码并提交
3. 确认登录成功，导航到报表页
4. 选择时间范围：上个月
5. 下载/提取销售数据
6. 用 CLI 聚合计算各产品线收入
7. 输出计算结果

↓ Agent Loop 执行，每步分解为

**工具调用层**（具体工具指令）
`browser_navigate` → `browser_screenshot` → `browser_click` → `browser_type` → `browser_click(submit)` → `browser_screenshot(确认)` → `browser_extract(table)` → `file_write(data.csv)` → `opencli_exec(python sum.py)` → ...

这三层各司其职：用户目标层是需求，步骤层是计划，工具调用层是执行。混淆三层会导致各种问题（如让 LLM 直接从目标跳到工具调用，跳过规划，容易在复杂任务中迷失方向）。

### 9.2 何时需要显式的任务规划层

对于**简单任务**（3-5 步以内，路径清晰），不需要显式的任务规划层。把用户目标直接给 Agent，让它在 Loop 中自然地规划和执行，效率更高。

对于**复杂任务**（10 步以上、有条件分支、需要多阶段数据流），建议在 Agent Loop 之上增加一个显式的任务规划层：先用 LLM 把目标分解为步骤列表，再把步骤列表注入 Agent 的初始上下文，让 Agent 按步骤执行。

这样做的好处是：

- Agent 不容易在复杂任务中"迷失"（有清单对照）
- 步骤完成后可以打检查点，失败时只需重做失败的步骤，而不是整个任务
- 步骤列表对用户也是透明的，方便人工监督

### 9.3 规划与执行的分离原则

规划和执行应该使用**不同的 LLM 调用**，甚至可以使用不同的模型。规划需要较强的逻辑推理能力（用较大的模型）；执行中的工具调用判断相对简单（可以用较小的模型降低成本）。

此外，规划的结果应该以**结构化格式**（如 JSON 步骤列表）输出，而不是自然语言描述。结构化步骤列表便于程序层追踪进度、处理失败、打检查点，也便于后续步骤依赖前序步骤的结果。

## 关键设计权衡

### 10.1 自主性 vs 可控性

Agent 越自主，需要人工干预越少，但出错的风险也越大。对于浏览器自动化，这个权衡尤为明显：

高自主性（Full-auto）适合：任务路径清晰、操作可回滚（如数据读取）、沙箱环境完善的场景。

低自主性（Ask 模式）适合：任务包含不可逆操作（删除数据、发送邮件、提交表单）、操作对象是生产系统、需要人工验证中间结果的场景。

**关键原则**：不可逆操作永远需要人工确认，无论系统有多成熟。

### 10.2 效率 vs 稳健性

频繁截图提高了稳健性，但消耗大量 token 和时间。减少截图提高了效率，但增加了"盲操"的风险。

这个权衡没有通用答案，取决于任务特性：对于高价值、操作复杂、路径多样的任务，宁可慢一点但稳；对于高频、路径固定的批量任务，可以适当减少截图频率，在固定节点才截图确认。

### 10.3 泛化性 vs 专用化

通用的 Agent（使用视觉 + 自然语言理解处理任何网页）具有最大的灵活性，但对网页变化有更强的抵抗力，开发成本也更高。

针对特定网站的专用 Agent（硬编码了页面结构、选择器、流程步骤）效率更高、成本更低，但网页一旦改版就可能失效。

**混合策略**：用通用 Agent 处理"探索"阶段（发现页面结构、定位元素），用专用逻辑处理"执行"阶段（已知路径的批量重复操作）。视觉接地用于初次探索和异常处理，CSS 选择器用于已知路径的稳定执行。

### 10.4 设计决策速查表

| 设计问题              | 推荐选择                   | 原因                          |
| --------------------- | -------------------------- | ----------------------------- |
| Agent Loop 的中止策略 | LLM 自主判断（end_turn）   | 最灵活，能适应任务复杂度变化  |
| 工具粒度              | 以"用户意图"为单位         | 降低 LLM 的决策负担           |
| 历史管理              | 保留头部 + 尾部，压缩中间  | 保留目标和最近上下文          |
| 截图策略              | 关键操作前后必截           | 视觉确认是最可靠的状态感知    |
| 错误处理              | 工具返回错误描述，不抛异常 | 让 LLM 看到错误并自主决策恢复 |
| Browser/CLI 数据传递  | 小数据内存，大数据文件     | 平衡效率和可靠性              |
| Approval 默认模式     | Ask（高风险操作）          | 安全底线优于效率              |
| 任务规划              | 复杂任务先规划再执行       | 防止 Agent 在长任务中迷失方向 |
| 状态设计              | 显式共享状态，检查点保障   | 程序层可靠性 > 上下文隐式传递 |

## 核心术语速查

| 术语             | 定义                                                                    |
| ---------------- | ----------------------------------------------------------------------- |
| Agent Loop       | 驱动 Agent 持续运行的 while 循环，每轮包含 LLM 调用和（可能的）工具执行 |
| ReAct 模式       | Reasoning + Acting，交替推理与行动的 Agent 范式                         |
| Observation      | 工具执行后返回给 LLM 的结果，是 Agent 感知世界状态的唯一渠道            |
| Tool Call        | LLM 在响应中声明的工具调用意图，包含工具名和参数                        |
| Context Window   | LLM 单次调用能处理的最大信息量，Agent 的"工作记忆上限"                  |
| Visual Grounding | 将视觉信息（截图）与操作意图（点击、提取）关联起来的能力                |
| Shared State     | 跨工具类型（Browser / CLI）的程序层共享数据结构                         |
| Approval Gate    | 工具执行前的人工审批或策略检查机制                                      |
| Checkpoint       | 任务中途的状态快照，用于失败后的恢复                                    |
| Sandbox          | 限制工具执行权限的隔离环境，是 Full-auto 模式的安全基础                 |
