# Tokenizer：把文字变成数字

<SeriesNav series="llm" />

上一篇的 MiniGPT 用的是字符级 tokenizer，每个字母对应一个 token，词表大小 65。在 64 token 的上下文窗口下，模型实际能看到的就是 64 个字母，约 10 个英文单词。作为对比，GPT-3 的窗口是 2048 token，GPT-4 是 128K，相差三到四个数量级。

字符级编码的代价是序列被拉得很长。同样一段文本，模型每跨一步只前进一个字母，注意力机制要算 <Math>{`O(n^2)`}</Math> 的相关度矩阵，序列翻倍，计算量翻四倍。窗口稍大，显存与算力成本便急剧上升。

一个直接的优化是把高频字符组合合并成一个 token。`the` 在英文文本里出现的频率极高，与其拆成 `t`、`h`、`e` 三个 token，不如分配一个独立编号，编码效率提升三倍。`ing`、`tion`、`Citizen` 这些常见词缀和单词同样压缩。词表从 65 扩到几百到几千之后，同样 64 token 的上下文，实际覆盖的字符数能翻两到三倍。

<TokenizationCompare />

这就是 BPE（Byte Pair Encoding）的思路，也是 GPT 系列一直在用的 tokenizer。

## 三种切法的取舍

把文字切成 token 大致有三种粒度。

字符级最简单，词表只有几十个，缺点是序列太长，模型上下文很快就被字母填满。词级反过来，一个单词一个 token，序列短，但词表要装下几十万个词。遇到训练时没见过的新词，比如 `ChatGPT`、`tokenizer`，词级 tokenizer 只能输出一个特殊 token `<UNK>`（unknown，未登录词）作为兜底——所有没见过的词都被压成同一个 `<UNK>`，模型完全不知道原文是什么。

子词级在两者之间。常见组合合并成一个 token，罕见的拆成更小的片段，再罕见的就退回到字节。词表大小可控（一般几千到十万），还能覆盖任意输入，没有未登录词的问题。

三种切法在几个关键维度上的差异：

| 维度 | 字符级 | 词级 | 子词（BPE） |
|---|---|---|---|
| 词表大小 | 几十 | 数十万 | 几百到十万 |
| Embedding 参数量（按 d=768） | ~5 万 | ~3.8 亿 | 50 万 ~ 7600 万 |
| 序列长度 | 最长 | 最短 | 居中 |
| 未登录词 | 不存在（所有字符都在词表） | `<UNK>` 兜底，信息丢失 | 拆成已知子词，不丢信息 |
| 代表使用者 | 早期 char-RNN | 早期 NLP（Word2Vec、GloVe）| GPT、LLaMA、Mistral 等所有现代 LLM |

词表每翻 100 倍，模型 embedding 层的参数量也翻 100 倍。BPE 用极小的词表加子词组合覆盖任意输入，编码效率和模型大小之间取得了最佳折中——这是它替代词级、统治当代 LLM tokenizer 的根本原因。

## BPE 在做什么

BPE 的训练过程是一个简单的循环：找出现频率最高的相邻 token 对，把它们合并成一个新 token，重复这件事直到词表大小达到预设值。

写成伪代码就是：

```text
初始词表 = 256 个字节（任何文本都能表示）
重复 N 次：
  1. 数一遍数据里所有相邻 token 对的频率
  2. 挑出频率最高的那一对 (a, b)
  3. 给 a + b 一个新编号，加入词表
  4. 把数据里所有 (a, b) 都替换成这个新 token
```

每一步要解的就是这个：

<Math block>{`(a^*, b^*) = \\arg\\max_{(a, b)} \\text{count}(a, b)`}</Math>

也就是从所有相邻对里挑出现次数最多的那个。

<BPETraining />

合并的顺序是有讲究的。BPE 按「最常见 → 次常见」的顺序逐条积累合并规则。编码新文本的时候，也得按训练时的顺序应用这些规则，否则就拼不出训练时看到过的那些大 token。

把 Tiny Shakespeare 喂进去，前 10 次合并是这样的：

merge  6: (',', ' ') → ', ' 出现 14,098 次

合并到 101 步时，`with` 已经凑齐了。201 步时，`sha` 也合上了。再往后会合出 `the `、`Citizen:`、`First ` 这种带空格、带标点的整段，模型每跨一步能拿到的信息也跟着越来越多。

## 写成代码

训练的核心循环大概十几行：

```python
def train(self, text, vocab_size):
    tokens = list(text.encode("utf-8"))   # 先变成字节列表

    for i in range(vocab_size - 256):
        pair_counts = self._count_pairs(tokens)  # 统计相邻对
        best_pair = max(pair_counts, key=pair_counts.get)
        new_id = 256 + i
        tokens = self._merge(tokens, best_pair, new_id)
        self.merges.append(best_pair)
```

编码新文本时按训练时的顺序依次套用这些合并规则：

```python
def encode(self, text):
    tokens = list(text.encode("utf-8"))
    for pair in self.merges:                # 顺序很重要
        new_id = 256 + self.merges.index(pair)
        tokens = self._merge(tokens, pair, new_id)
    return tokens
```

解码反过来——每个 token id 对应一段字节，按 id 查表后拼起来再 UTF-8 解码即可：

```python
def decode(self, ids):
    return b"".join([self.vocab[i] for i in ids]).decode("utf-8")
```

## 词表开多大合适

同一份莎士比亚文本，把 vocab_size 从 65 一路开到 4000，压缩率和训练时间是这样的关系：

<VocabSizeChart />

vocab_size 翻倍，压缩率大约多 0.5 到 0.7 倍，但越往后收益越小。从 512 到 1000 多压了 0.53 倍，从 2000 到 4000 只多了 0.67 倍。训练时间却几乎是线性涨的——纯 Python 实现里，每多一次合并都要扫一遍整个序列。

词表太小，序列长，模型需要更大的上下文才能看到足够内容；词表太大，embedding 表占的参数就多了起来，罕见 token 的样本又不足，反而学不好。GPT-2 选的是 50257，LLaMA 是 32000，GPT-4 用了 100K。这个 1MB 的小数据集，512 已经够用。

## 同一段文本能装多少

把这件事拉到上下文长度上看会更直观。同样 64 个 token 的窗口，三种切法实际能装下的内容差距很大：

<ContextCoverage />

字符级只能勉强装下两三句台词，BPE-512 能多装一倍，BPE-4000 能装下整段对白。模型看到的上下文越长，生成出来的故事就越能保持人物、场景的一致。

## 中文怎么办

到这里看下来，BPE 像是个万能解。但它最早是为英文设计的，遇到中文会有点尴尬。

中文一个字是 3 个 UTF-8 字节，如果直接拿英文训练好的 byte-level BPE 编码中文，常见情况是一个汉字会被切成 2 到 3 个 token。GPT-2 就是这样——`你好`这种最常见的词都要 5 到 6 个 token，看着很浪费。

GPT-4 换了一套 tokenizer（`cl100k_base`），训练数据里加了大量中文，结果好得多：常见的双字词能合成一个 token，单字也只占一个 token。

<TokenizeBilingual />

这就是为什么同样 8K 上下文，处理英文与处理中文的有效长度差异显著。中文每个 token 承载字数较少，实际可见段落更短。

## 三个模型，换上 BPE

把上一篇的字符级 tokenizer 换成 BPE-512，模型结构不动，训练步数不动，验证集 loss 和生成效果都有变化：

| Tokenizer | 上下文（64 token 实际覆盖） | Val Loss | 生成效果 |
|---|---|---|---|
| 字符级（vocab=65） | 约 64 字符 ≈ 10 单词 | 1.58 | 句子偶尔断裂 |
| BPE-512 | 约 125 字符 ≈ 20 单词 | 1.42 | 多轮对话连贯 |

## 和工业界的距离

| 环节 | 这个项目 | GPT-4 级别 |
|---|---|---|
| 算法 | 基础 BPE | BPE + 正则预分词 + 特殊 token |
| vocab_size | 512 | 100,000+ |
| 训练数据 | 1MB 英文 | TB 级多语言 |
| 编码速度 | ~5K tokens/s（纯 Python） | ~1M tokens/s（Rust/C++） |
| 中文支持 | UTF-8 字节级，能用但低效 | 专门优化的中文 token |

差距主要在两块。一块是速度——`_count_pairs` 每次都要扫全序列，工业级实现（tiktoken、SentencePiece）核心循环用 C++ 或 Rust 写，再加上正则预分词（先按空格、标点切开再做 BPE，避免跨词合并），快两个量级。另一块是数据——多语言数据让 tokenizer 学到的合并规则覆盖更广，中文、日文、代码这些场景都不会再是字节级的浪费。
